# Issue 2301: cancelled Claude background work and false recovery notice

The affected run solved [links-notation#315](https://github.com/link-foundation/links-notation/issues/315) with Claude Code 2.1.282 in print mode and opened [PR #319](https://github.com/link-foundation/links-notation/pull/319). Its container was tracked as `933a1ab3-1630-48a3-b35a-3087d7b2603c`; the Claude session was `85671f31-4459-422e-8fef-04ee03fd3aa0`. The run did real work, but ended before its five port agents finished. Hive Mind then misread Claude's shutdown events as a user rejection, and its separate OOM notice claimed a replacement session had started when none had.

## Requirements and root causes

1. **Finish authorized work without a false user-feedback request.** The string “The user doesn't want to proceed” came from Claude Code's shutdown of still-running background subagents, not from a Hive Mind tool classifier or a real user. `--no-tool-check` skipped Hive Mind connection checks, `--dangerously-skip-permissions` bypassed Claude tool approvals, and `permission_denials` was empty. The stream parser kept updating its final tool verdict _after_ Claude's authoritative `result`, so the synthetic cancellation overwrote success. Fix: ignore post-result tool outcomes in one-shot print mode, log cancellation as a distinct event, and prompt both Claude and Codex to finish dependent work before ending a turn. Codex was not used in this incident; its existing noninteractive runner uses `--dangerously-bypass-approvals-and-sandbox`.
2. **Actually finish pending Claude work.** Print mode ends when the turn ends. An assistant message saying it will wait cannot receive a later notification. The result itself confirms five system-killed subagents. Fix: set Claude Code's documented `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` for one-shot runs, detect a successful result that still reports stopped tasks, and make one bounded same-session continuation with an explicit instruction to redo and await unfinished work. If that attempt also ends incomplete, report a real failure instead of declaring the issue solved. Streaming-input sessions retain their existing long-running behavior. The one-attempt cap prevents an endless retry loop.
3. **Resume after an OOM event followed by exit 1.** Docker's `OOMKilled` flag can coexist with a surviving main process: here the footer and container both say exit 1, not a SIGKILL exit. The existing monitor remembered only an exit-0 survivor, classified this exit as an ordinary failure, and only called recovery for a killed session. Fix: persist the earlier OOM observation for an ordinary exit, classify exit-1 plus OOM observation as a failed run affected by a child OOM event, and run the existing bounded `--on-session-kill=resume` path for that case. The new monitor regression verifies that a real replacement is launched with `--resume` and its ID appears in both surfaces.
4. **Report what actually happened.** The old PR notice treated “survived an OOM event” as “replacement started” because it combined `recovered || resumed`. Fix: separate survived, failed-after-OOM, and actually restarted states. State a new session was started only after the launch succeeds and include its ID. Describe the earlier container OOM and the later host-memory reading in their proper time order.
5. **Keep experiments from starving concurrent work.** The reported host had three active tasks and nearly exhausted RAM during stack probes. Fix: give each Docker Telegram task a default 25% host-memory cgroup limit (overridable with `--container-memory` / `TELEGRAM_CONTAINER_MEMORY`) and add explicit bounded-experiment guidance to Claude and Codex prompts. Docker documents `--memory` as a per-container hard limit and `--memory-swap` as the swap control: [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/). This does not guarantee that a single task's tests fit within the default; operators can raise it for larger jobs.
6. **Preserve and study the evidence.** This directory contains the logs, issue and PR comments, event reconstruction, alternative explanations, test coverage, and upstream references. There is no evidence of a Codex classifier failure in this incident. A separate Codex trace would be needed to diagnose one.

## Upstream and alternative solutions

Claude Code's [environment-variable documentation](https://code.claude.com/docs/en/env-vars) describes `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`. [anthropics/claude-code#85066](https://github.com/anthropics/claude-code/issues/85066) reports the same silent success with orphaned subagents; [this follow-up](https://github.com/anthropics/claude-code/issues/85066#issuecomment-5842704259) provides the present run's reproduction pattern, workaround, and suggested CLI fix. [#89495](https://github.com/anthropics/claude-code/issues/89495) provides a small `claude -p` Bash reproduction and confirms the environment-variable workaround; [#82235](https://github.com/anthropics/claude-code/issues/82235) describes a related post-turn task-notification error. An upstream fix could await every pending child before emitting success, or reject background dispatch in print mode. Keeping stream-json input open is another possible host integration, but it would change the runner's session lifecycle more substantially than the current bounded continuation.
