# Case study: a `solve` session stuck for 5+ hours after its final log (issue #4091)

Issue: [#4091](https://github.com/link-assistant/hive-mind/issues/4091) "Session stuck for 5+ hours after posting its final log: watch loop waits without limit on a HEAD workflow run held in a concurrency queue (status pending, 0 jobs); no finish/auto-continue, Telegram still shows Executing".
Implementation: [PR #4092](https://github.com/link-assistant/hive-mind/pull/4092).
Research date: 2026-11-19 UTC.

## Summary

A `solve` run (hive-mind 2.39.14, Docker isolation, `--attach-logs --verbose`) finished its AI work and spent 34 minutes sanitizing and uploading a 113 MB log. It then posted "🤖 Solution Draft Log … Now working session is ended" on the pull request. After that it polled the pull request for another **5 hours** (135 checks) without telling anyone what it was waiting for. An operator stopped it with `/stop`. The container was SIGKILLed about 10 s later, the interrupted-session log was lost, and the kill notice said `SIGKILL; cause unknown`.

The default `--auto-restart-until-mergeable` loop was waiting on **one workflow run on the HEAD commit**. That run sat in `status: pending` with **zero jobs** because its workflow uses a repository-wide `concurrency` group (`cancel-in-progress: false`, `queue: max`), and runs from other pull requests held the group. All 20 check runs had passed and GitHub reported the PR as `mergeable: true, state: CLEAN`.

The full logs are in a private repository. This study uses only the sanitized excerpts quoted in the issue, so it has no `data/` folder.

## Root causes

1. **An unbounded wait on a HEAD run that had not started.** `getMergeBlockers` (`src/solve.auto-merge-helpers.lib.mjs`) turns every non-`completed` workflow run on HEAD into a `ci_pending` blocker. For `ci_pending`, `watchUntilMergeable` only logs `⏳ Waiting for CI:` and sleeps. Its only limit is the 24 h watch timeout.
2. **The #4048 stuck-CI monitor skips `pending` runs on purpose.** `findGhostQueuedRuns` keeps only `status === 'queued'`, so the "CI wait stuck" notice was never posted for a `pending`, `waiting` or `action_required` run.
3. **The Telegram monitor knew nothing about the watch phase of `/solve`.** `/fix` prints `[HIVE-MIND FIX]` phase markers, but `/solve` printed none, so `⏳ Executing...` stayed on screen.
4. **The log comment claimed the session had ended.** It is posted before `startAutoRestartUntilMergeable`, which is on by default.
5. **Waits after the final log had no heartbeat and no deadline.** This covers the sanitize, the upload, the GitHub probes of every check and the CI wait itself.
6. **`/stop` lost the log and the reason.**
   - The interrupt handler started re-sanitizing the whole 114 MB log, but start-command allows only about 10 s before SIGKILL.
   - The watch loop's in-flight check kept running.
   - The kill diagnostics did not use the CTRL+C line in the log, so they reported `cause unknown`.
7. **Logging gaps.**
   - Watch-loop lines in stdout had only a local `h:mm:ss AM` time.
   - `checkForIssueMetadataChanges` received the mirroring `$`, so the full issue JSON was printed on every check (134 copies).

If every check passed, the only blockers are runs that have not started (concurrency queue or approval), and those runs are older than `HIVE_MIND_STUCK_PENDING_RUN_MINUTES`, the loop logs this on the **first** check and posts **one** PR notice per commit. ## Known limit: start-command's stop grace period

`/stop` runs `$ --stop`. start-command sends CTRL+C and then SIGKILL about 10 s later (`docker stop` behaves the same way). hive-mind cannot set that period. This PR therefore keeps the interrupt work small enough to fit in it: the watch loop stops starting checks, and only a tail of at most 2 MB is uploaded. For an operator stop, the kill notice already blames the stop instead of saying "cause unknown". If the upload still does not finish in time, the watcher's start-command capture is still attached, as before.
