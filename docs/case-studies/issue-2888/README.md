# Case study: issue #2888 — a fresh kill recovery cannot resume a Codex thread

When the bot cannot recover a killed task in its own container, it starts a **fresh** container with `solve … --resume <tool session id>`. For Codex that could never work: solve runs Codex with a repository-scoped `CODEX_HOME` inside the task container, and only `~/.codex/auth.json` and `~/.codex/sessions` are mounted. The thread's rollout died with the killed container, so the new run failed within a minute with `no rollout found for thread id …`. A second fresh run was refused by solve's own disk preflight (exit 75) before it did anything, and it still used up a recovery attempt.

Runtime at the incident: hive-mind 2.34.0, start-command 0.35.4, Docker 29.6.1 with the containerd image store; `/codex` tasks in `konard/hive-mind-dind:2.34.0` containers. The fix was checked with codex-cli 0.162.1.

## Requirements

From the issue's "Expected" and "Suggested fix" sections:

1. R1. Before the fresh launch, copy the thread's rollout out of the stopped container (`docker cp` works on stopped containers) and make it available to the new container, **or** keep the repository-scoped `CODEX_HOME` on a mounted volume in the first place.
2. R2. If the rollout cannot be recovered, launch without `--resume` (`--auto-continue` on the existing PR) instead of a run that is certain to fail.
3. R3. A launch refused by the disk preflight (exit 75, nothing attempted) does not count as a recovery attempt, and is retried when space frees up.
4. R4. Check the same for every tool with `--resume` (claude, agent, gemini, qwen): where does each keep its session, and is it mounted into task containers?
5. Expected: a fresh recovery run either has the thread available or does not ask for it.

## What remains

- **agent, gemini, qwen and opencode in Docker.** Their session store is not mounted, so `resolveFreshRecoveryCommand` drops their `--resume` in a new container, and the notice says so, as it does for an unrecoverable Codex thread. It reads `DOCKER_ISOLATION_TOOL_MOUNTS`, so a tool whose session folder is mounted later keeps its resume with no change here. Mounting those folders needs the paths each CLI version uses, which this branch did not re-verify. A claude task with `--use-router` gets no `~/.claude` mounts and drops its resume too.
- **claude in Docker** is kept without checking that the transcript exists under the mounted `~/.claude/projects`. It normally does, because Claude Code writes there directly.
- **`--use-router` Codex tasks** always drop the resume, because router containers mount no vendor state.
- **The bounds are per bot process.** The deferral counter is persisted with the session (`killRecoveryDiskDeferrals`), but a wait in progress is lost when the bot restarts. Issue #2890 (PR #2896) covers queues that survive restarts.

## Related components

- Codex CLI: `codex exec resume <id>` reads only `$CODEX_HOME/sessions` ([openai/codex](https://github.com/openai/codex), `docs/config.md`, "CODEX_HOME"). A brand-new `CODEX_HOME` whose `sessions` links to a shared directory resumes the thread; without the link it fails with exactly the router#727 error (checked with codex-cli 0.162.1).
- `docker cp` copies files out of a stopped container ([Docker docs](https://docs.docker.com/reference/cli/docker/container/cp/)).
- `EX_TEMPFAIL` (75) in `sysexits.h`: a temporary failure that should be retried, which is how solve's disk preflight (issue #2160) uses it.
- The disk-headroom wait (`waitForSnapshotDiskHeadroom` in `src/kill-recovery-snapshot-guard.lib.mjs`) is shared with issue #2889.

## Reproduction

```bash
npm ci
node --test tests/fresh-resume-2888.test.mjs
```

By hand: run a `/codex` task with Docker isolation on a hive-mind release without this branch, kill its container, and force the fresh fallback (for example, remove the stopped container before the recovery starts). The new container fails with `no rollout found for thread id …`. On this branch the rollout is in the mounted `~/.codex/sessions`, so the thread is resumed; if it is not there, the recovery starts a new Codex session on the same branch.
