# Case study: issue #3614 — the bot polls Docker and session state up to ~95 times a minute

- Issue: https://github.com/link-assistant/hive-mind/issues/3614
- Pull request: https://github.com/link-assistant/hive-mind/pull/3615
- Reported on: hive-mind 2.39.2, start-command 0.37.8, a 6-CPU host with 2–3 docker-isolated tasks (2026-10-20)
- Upstream report (start-command's own monitor loop): https://github.com/link-foundation/start/issues/238, fixed in start-command 0.39.0; the images pin 0.39.2, including the follow-up below
- Follow-up upstream report (0.39.0 keeps retrying failed rounds when cgroup counters can't be read): https://github.com/link-foundation/start/issues/247, fixed in 0.39.1 and included in the pinned 0.39.2

## What was measured

| Window (UTC)      | Bot's child processes | Bot's own code | Processes started per minute                                                                                                                                  |
| ----------------- | --------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 20:03:31–20:03:46 | 0.52 cores            | 0.02 cores     | `docker inspect -f {{.Id}}` 87, `docker inspect -f {{.State.Running}}` 75                                                                                     |
| 20:20:56–20:21:01 | 0.99 cores            | 0.10 cores     | `sh -l -c '…/$'` 95, `bun $ --status <session>` 95, `docker inspect -f {{.State.Running}}` 71, `sh -l -c docker` 59, `sh -c pgrep -l` 47, `sh -l -c which` 47 |

## Root causes

1. **No shared result per session.** The session monitor (every 30 s), the queue consumer's processing count (`canStartCommand` → `getExternalProcessingSnapshot`, several times per loop while items wait), `/limits`, `/queue`, `/log` and `/terminal_watch` (every 2.5 s per watch) each ran their own `$ --status <session>`. `isSessionRunning()` could run it twice for the same session.
2. **Every `$` call was two login shells.** command-stream's `$` wraps each command in `/bin/sh -l -c`, and `findStartCommandBinary()` ran `` $`which $` `` before every start-command call without caching it. So one status check was `sh -l -c which $` + `sh -l -c $ --status …` + the `bun` process + its own `docker inspect`.
3. **One process per container per caller.** Backend liveness ran `docker inspect` (through `sh -l -c`) per container, `screen -ls` per session, and `pgrep -l -x <tool>` (through `sh -c`) once per tool.
4. **Overlapping timers.** The session monitor, `/top`, the bidirectional-interactive pollers and the Formal AI / router sidecar maintenance used `setInterval(asyncTick)`. A slow Docker daemon made ticks pile up, each starting its own processes.
5. **Outside hive-mind:** start-command's detached monitor for each docker-isolated task samples cgroup memory every second (`CGROUP_SAMPLE_INTERVAL_SECONDS = 1` in `src/lib/cgroup-memory.js` of start-command 0.37.8), running `docker inspect -f {{.State.Running}}` and, when the local cgroup is unreadable, `{{.HostConfig.CgroupnsMode}}` each round. That is the 36–47 checks per minute per task in the issue. Reported upstream as link-foundation/start#238; hive-mind cannot change that loop. start-command 0.39.0 fixed it. It samples every 5 s (`START_COMMAND_CGROUP_SAMPLE_INTERVAL_SECONDS`), looks up the namespace once, keeps one long-lived `docker exec -i` per task, and asks for `{{.State.Running}}` only after a failed round (start#238, #242). Its `$ --status` / `$ --list` also decode the store once and answer every docker probe with one `docker inspect` (start#243). The images pin 0.39.2, which also stops sampling permanently unreadable counters and backs off transient failures (start#247).

## What changed

- **`src/status-check-cache.lib.mjs`** — one in-memory cache shared by the whole bot. A key is checked at most once per `HIVE_MIND_DOCKER_STATUS_MIN_INTERVAL_MS` (default **5000 ms**, so at most **12 checks per minute** per probe; bot option `--docker-status-min-interval-ms`). Callers that arrive while a check runs await the same promise. The interval counts from when a check finished. Failures are not cached. `invalidate()` / `invalidateSessionStatus()` drop an entry when the bot itself starts or stops a task; a check that was already running when it was invalidated answers its callers but is not stored. `0` disables the reuse and keeps the de-duplication.
- **`src/status-probes.lib.mjs`** — `runProbe()` runs `docker`, `screen`, `tmux`, `pgrep` and `$` with `execFile` (no shell, with a timeout; a missing binary is exit 127). Docker liveness for all containers comes from one cached `docker ps`, screen liveness from one cached `screen -ls`.
- **`src/start-command-cli.lib.mjs`** — `findStartCommandBinary()` resolves `$` from `PATH` once and caches it; `$ --status` / `$ --list` run through `runProbe()`. A missing binary is retried once a minute through the existing login-shell lookup. A runtime only available on the login-shell PATH retains the existing query fallback.
- **`src/isolation-runner.lib.mjs`** — `querySessionStatus()` and `listIsolationSessions()` read the shared cache (callers get a copy); `isSessionRunning()` and the backend probes reuse it; launching and stopping a session invalidate it; container exists / writable-layer size probes run `docker` directly; Docker liveness accepts full IDs and slash-prefixed names, with a shared direct inspect for abbreviated IDs so Docker resolves ambiguity; `checkTmuxSessionRunning()` now reads tmux's exit code (it used to report a missing session as running).
- **`src/telegram-solve-queue.helpers.lib.mjs`** — `getRunningProcesses()` answers every tool from one cached `pgrep -l -x claude|codex|…` run without a shell.
- **`src/serial-poller.lib.mjs`** — `startSerialPoller()` schedules the next tick with `setTimeout` only after the current one settled. Used by the session monitor (with a per-session budget so one slow completion does not hold up the others), `/top` and the bidirectional-interactive pollers. The sidecar maintenance timer skips a tick while the previous one runs.
- **`src/version-info.lib.mjs`** — `/version` answers share one `getVersionInfo()` result for 30 s instead of starting ~66 shell commands per message.
- **`src/limits.lib.mjs` / `src/limits-subscription.lib.mjs`** — concurrent cold-cache calls share one GitHub, CPU, memory, disk or subscription probe. Existing TTLs remain unchanged; failures can be retried, and invalidation detaches pending loads. Eight simultaneous requests previously started eight probes.
- **Images** — `Dockerfile`, `Dockerfile.dind`, `coolify/Dockerfile` and `Dockerfile.e2e` pin start-command **0.39.2** (row 30). `tests/start-command-0.39-compat-3614.test.mjs` checks that its status record parses, and that its new exit reason `killed (docker daemon restart)` (start#241) is not read as memory exhaustion.
- **Lint** — `hive-mind/no-login-shell-probe` flags `$`-template probes (`docker`, `which`, `screen`, `tmux`, `pgrep`, `ps`, start-command) on bot paths, which run through `sh -l -c`; `hive-mind/no-overlapping-interval` flags `setInterval` with an async callback. Existing call sites are listed with reasons in `eslint-rules/baselines/`, so only new ones fail. The #3206 sync-I/O rules (`hive-sync-ok`) still block new sync calls on bot paths.

"Bot: `docker` per task" counts the one `docker inspect` inside each `$ --status` plus a third of the bot's `docker ps`, which answers for all containers at once (44.6/min in total on the default run: 32.7 inside `$ --status`, 11.9 `docker ps`). Each probe stays under 12 calls a minute. This stress test deliberately asks for both a session query and an independent backend check, so its combined Docker count is higher; the idle-chat verification below uses the actual isolation-state reconciliation path. On `main` the bot's numbers are bounded only by how fast the host starts processes: with 0.38.0 each `$ --status` was slower, so fewer ran. The issue measured 0.52–0.99 cores for the bot's children and 36–47 monitor rounds per task per minute with 0.13–0.17 cores on the reporter's host. With this branch and 0.39.0 the bot runs under 12 `$ --status` per task per minute and its child CPU drops by about 90 %. The monitors start 76 % fewer `docker` processes and use 71–77 % less CPU.

The monitor counts above are the fallback path: without the `memory` controller the counters can never be read, so 0.39.0 runs one `docker exec` + one `docker inspect` per task every 5 s and never records a sample. That gap is reported as https://github.com/link-foundation/start/issues/247. On a host with readable counters, 0.39.0 keeps one long-lived `docker exec -i` per task (link-foundation/start#242: 12 rounds took 1 `docker exec` and 1 liveness probe in its tests). Readable-counter streams are exercised by the finite fixture below; the live sandbox has no memory controller.

The reporter's production deployment was not accessed. The measurements use real Docker tasks and `/proc` child CPU in this sandbox, one of the measurement methods requested by the issue.

## Follow-up verification (2026-10-24)

The feedback asked whether start-command delivers everything needed. The npm registry now publishes **0.39.2**. Its 0.39.1 changes include start#247 (merged in [start PR #248](https://github.com/link-foundation/start/pull/248)): exit 3 stops both stream and fallback sampling, while transient failures back off from 5 to 10, 20, 40 and 60 s. Longer configured intervals remain the floor. The 0.39.2 change concerns log sanitization and preserves these fixes. All four images and the test dependency pin 0.39.2.

`tests/start-command-sampler-3614.test.mjs` runs in the default suite against the actual installed npm package. It calls `experiments/issue-3614-upstream-check.mjs` with the finite shell fixture from start PR #248. The fixture runs the real generated sampler and in-container scripts; it advances at most four rounds. Eight checks cover permanent failures, the fallback read, transient backoff, the cap, a longer interval, readable local counters, one remote stream, and disabling sampling. Four checks fail against 0.39.0; all eight pass against 0.39.2. Before/after output: `experiments/issue-3614-logs/sampler-0.39.0-before.txt` and `sampler-0.39.2-after.txt`.

Reproduce against either published version:

```sh
npm install --prefix /tmp/start-check --ignore-scripts start-command@0.39.2
node experiments/issue-3614-upstream-check.mjs /tmp/start-check/node_modules/start-command
```

Live verification with 0.39.2 and three real Docker tasks, a 61 s measurement window and no interval override: the four synthetic callers produce **11.8 `$ --status` per task per minute**, with **0.124 cores** in bot children. After startup the detached monitors produce **zero Docker processes and zero measured CPU** on this host with unreadable counters. All three tasks remain running. The stress run still requests an independent shared `docker ps` alongside `$ --status`; its aggregate is 15.8 Docker processes/task/minute. It must not be described as a combined count of at most 12. Full output: `experiments/issue-3614-logs/live-start-command-0.39.2-branch-bot-default.txt`.

The `--idle-chat` variant runs `getIsolationSessionState()` and the default `runDockerCpuPenaltyPass()` every 30 s, matching the monitor's status and CPU sampling work when the chat is idle. Its result is recorded separately below.

Idle-chat result with three tasks over 65 s: **1.8 `$ --status` per task/minute**, **4.3 combined Docker processes per task/minute** (including the shared listing and the default CPU penalty sampler), **0.035 cores** in bot children, and **0.001 cores** in bot code. Detached monitors start no Docker processes after initialization. Every task remains running. This verifies the requested ≤12/minute bound and the CPU reduction in the idle-chat scenario. Output: `experiments/issue-3614-logs/live-start-command-0.39.2-branch-bot-idle.txt`.
