# Черновики Formal AI (languages: [en](FORMAL-AI-DRAFTS.md) • [zh](FORMAL-AI-DRAFTS.zh.md) • [hi](FORMAL-AI-DRAFTS.hi.md) • ru)

Каждая задача, открытая в этом репозитории, в течение нескольких минут получает одну попытку от Formal AI — в ветке, от которой никто не зависит. Неудачная попытка не стоит ничего. Удачная экономит первый коммит. Провалившаяся попытка тоже не расход: она проваливается публично, с приложенными свидетельствами сессии, и именно этот провал становится исходным материалом для следующего улучшения мета-алгоритма.

Это ответ на [issue #2233](https://github.com/link-assistant/hive-mind/issues/2233).

## Что запускается

`.github/workflows/formal-ai-draft.yml` срабатывает на `issues: opened` — а не на специально выставленную метку, потому что цель в объёме свидетельств за день, а не в том, чтобы человек решал, какая задача достойна попытки. Внутри опубликованного образа `konard/hive-mind:<version>`, где `<version>` — версия из `package.json` извлечённого workflow, выполняется одна команда:

```bash
solve <issue-url> \
  --tool agent \
  --model formal-ai \
  --attach-logs \
  --development-log \
  --verbose \
  --attribution formal-ai \
  --no-auto-restart-until-mergeable \
  --no-auto-restart-on-uncommitted-changes \
  --log-dir /home/box/logs
```

Это собственный путь Hive Mind, поэтому черновики являются непрерывным и неподделываемым измерением того, становится ли `solve --model formal-ai` лучше на реальных задачах в репозитории, которому принадлежит `solve`.

Получившийся коммит несёт четыре трейлера Formal AI и пакет свидетельств ([#2229](https://github.com/link-assistant/hive-mind/issues/2229), [#2230](https://github.com/link-assistant/hive-mind/pull/2230), v2.24.0):

```
Formal-AI-Session: ses_…
Formal-AI-Model: formal-ai
Formal-AI-Evidence: dev/log/self-authored/issue-<n>/evidence
Formal-AI-Pull-Request: https://github.com/link-assistant/hive-mind/pull/<n>
```

Автор каждого коммита в ветке — `github-actions[bot]`. Личность задаётся через `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`, а не через файл конфигурации, поэтому она действует внутри контейнера независимо от того, чей `HOME` смонтирован (это измеряет `experiments/issue-2233/probe-git-identity.sh`).

Четыре флага выбраны намеренно, а не унаследованы:

| Флаг                                       | Почему                                                                                                                                                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--attribution formal-ai`                  | Трейлеры и пакет свидетельств — смысл всего упражнения, поэтому они включаются принудительно, а не оставляются на усмотрение `auto`.                                                                         |
| `--no-auto-restart-until-mergeable`        | По умолчанию включён. Если его оставить, один запуск следит за проверками pull request и перезапускает модель до зелёного статуса — до 24 часов. Политика ниже говорит: этим занимается _следующий_ запуск.  |
| `--no-auto-restart-on-uncommitted-changes` | По умолчанию включён. Если его оставить, каждый незакоммиченный файл перезапускает модель — до пяти дополнительных сессий за один запуск. Политика отказов действует и здесь: повтор — это следующий запуск. |
| `--log-dir`                                | Журнал сессии выносится из контейнера через bind-mount и выгружается как артефакт workflow, поэтому его можно прочитать даже тогда, когда pull request вообще не был открыт.                                 |

### Образ, бинарник и собственное состояние Formal AI

- Скрипт явно скачивает `konard/hive-mind:<version>` и повторяет попытку при тайм-ауте реестра через 15 с, 30 с, 1 мин и 2 мин, поэтому в контейнере работает тот же hive-mind, что и скрипты рядом с ним. Ещё не опубликованный тег (версия поднята в `main` до завершения релиза) заменяется на `konard/hive-mind:latest` с предупреждением. Вход `image` или переменная `FORMAL_AI_DRAFT_IMAGE` используются как есть.
- Сервер Formal AI, который запускает сессия, получает `FORMAL_AI_CACHE_DIR` в своём домашнем каталоге. Formal AI всё равно пишет `data/cache/derivations/` в клон, поэтому этот каталог, как и `.formal-ai/`, исключён из проверки незакоммиченных изменений и из работы, сохраняемой в ветках `recovery/<branch>`: это состояние инструмента, а не работа пользователя.
- Контейнер запускается с `--rm`, поэтому комментарий об ошибке никогда не указывает на путь внутри него. Он ссылается на запуск workflow, артефакт которого содержит журнал сессии.

### Проверки в pull request

Pull request, открытый токеном по умолчанию, не запускает `pull_request`, а проверки, запущенные на его ветке, не привязаны ни к одному pull request. Поэтому задание `report-checks` публикует каждый запущенный прогон как статус коммита (`dispatched / release.yml`, …) на головном коммите черновика и обновляет его до завершения прогона, чтобы черновик показывал свои проверки.

`--auto-merge` и `--auto-close-pull-request-on-fail` не передаются никогда. Оба по умолчанию выключены; `tests/formal-ai-draft-2233.test.mjs` проверяет, что они и остаются отсутствующими, потому что включение любого из них молча сломало бы политику отказов.

## Политика отказов

Это то, что нужно прочитать прежде, чем трогать черновик.

1. **Провалившийся черновик остаётся открытым и красным.** Его не чинят. Его не откатывают. Он ждёт, пока не преуспеет более поздний запуск. Красный цвет — это и есть измерение; сделать его зелёным вручную значит уничтожить измерение.
2. **Черновик никогда не правят руками и не вливают.** Workflow возвращает pull request в состояние черновика после сессии (solve помечает его готовым к ревью в конце сессии — см. [#2123](https://github.com/link-assistant/hive-mind/issues/2123)/[#2182](https://github.com/link-assistant/hive-mind/issues/2182)), а GitHub отказывается вливать черновик. Если в черновике случайно оказалось верное изменение, правильная реакция — отметить это в задаче и дать обычному запуску создать обычный pull request, а не принимать ветку черновика.
3. **Плохой черновик закрывают, а дефект заводят на мета-алгоритм.** Не патчат в ветке. В новой задаче нужно ответить на вопрос «почему алгоритм это произвёл», а не «как сделать этот diff правильным». Сошлитесь на закрытый черновик и его журнал сессии из новой задачи.
4. **В ветку черновика никогда не попадает человеческий коммит.** Человеческий коммит делает ветку непригодной как свидетельство: уже нельзя сказать, что именно произвела модель. Если ветке нужен человеческий коммит, значит нужна другая ветка.

Черновик опознаётся по метке `formal-ai-draft` (workflow создаёт её, если её ещё нет) и по имени ветки `issue-<number>-<suffix>`.

## Настройка

Настройка не требуется. Все workflow с правом записи используют один resolver: GitHub App (`AUTOMATION_APP_ID` и секрет `AUTOMATION_APP_PRIVATE_KEY`) → один секрет `AUTOMATION_TOKEN` → встроенный `github.token`. Выбирается первый доступный слой. Для токена нужны права записи contents, issues, pull requests и Actions. `FORMAL_AI_DRAFT_IMAGE` остаётся необязательной переменной (по умолчанию `konard/hive-mind:<version>`).

Pull request с токеном по умолчанию может создать проверки, ожидающие одобрения. Workflow сразу запускает `release.yml`, `security.yml`, `links.yml` и `workflows.yml` через `dispatch-checks` на ветке черновика с `mode=checks`. Релиз требует явного выбора режима и ветки `main`. Отсутствие секретов не отменяет попытку; сводка показывает слой. Ежедневная проверка считает реальные попытки за семь дней. Она также падает, когда последние пять запусков черновика закончились одним и тем же `decision_code` или одной и той же первой ошибкой, называет её и ссылается на открытую задачу, которая её отслеживает (или просит её завести). Каждое задание черновика записывает оба значения как аннотации, поэтому сводка запуска объясняет, почему черновик красный.

Общие actions ещё не опубликованы: [link-foundation/.github#1](https://github.com/link-foundation/.github/issues/1). Пока используются совместимые локальные actions в `.github/actions/`.

## Запуск черновика из другого репозитория

Workflow переиспользуемый (`workflow_call`), поэтому `link-assistant/formal-ai` может проверить сборку на реальной задаче до релиза:

```yaml
jobs:
  draft:
    uses: link-assistant/hive-mind/.github/workflows/formal-ai-draft.yml@main
    with:
      issue_number: '42'
      formal_ai_binary_artifact: formal-ai-linux-x64
    secrets: inherit
```

| Вход                        | Значение                                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `issue_number`              | Задача в репозитории вызывающего. Не указывайте, если вызывающий сам запускается на `issues: opened`.                                |
| `image`                     | Образ hive-mind вместо `konard/hive-mind:<version>`.                                                                                 |
| `formal_ai_binary_artifact` | Имя артефакта вызывающего запуска с файлом `formal-ai`. Он монтируется только для чтения поверх `/usr/local/bin/formal-ai` в образе. |
| `hive_mind_repository`      | Репозиторий, чьи скрипты черновика извлекаются (по умолчанию `link-assistant/hive-mind`).                                            |
| `hive_mind_ref`             | Ref этого репозитория (по умолчанию — его ветка по умолчанию).                                                                       |

Бинарник должен работать на Ubuntu-основе образа (glibc). При вызове workflow не запускает проверки этого репозитория и его ежедневную проверку; `issues: opened` здесь работает как раньше.

## Как отказаться и как перезапустить

- Добавьте метку `no-formal-ai-draft` в шаблон задачи или на саму задачу до её открытия, чтобы подавить попытку.
- Задачи, открытые ботом, пропускаются: две автоматизации, кормящие друг друга, дают шум, а не свидетельства.
- Чтобы повторить попытку, запустите workflow вручную (`Actions → Formal AI Draft → Run workflow`), указав номер задачи. Ручной перезапуск трактуется как свежее событие `opened`.

## Как читать провалившийся черновик

1. Журнал сессии прикреплён к pull request флагом `--attach-logs`.
2. Если pull request не был открыт, тот же журнал доступен как артефакт `formal-ai-draft-session-<issue>` у запуска workflow и хранится 30 дней. Аннотации запуска называют первую ошибку, записанную сессией.
3. В ветке каталог `dev/log/self-authored/issue-<n>/evidence` содержит `agent-stream.jsonl` и `session-id.txt` — собственную запись модели о том, что она делала, а не пересказ Hive Mind.

## Когда formal-ai опубликует свой composite action

[Issue #2233](https://github.com/link-assistant/hive-mind/issues/2233) просит установить переиспользуемый action, который `link-assistant/formal-ai` выделяет из своего `self-authored-pull-request.yml`. На момент написания этот action ещё не опубликован — свидетельства собраны в [`docs/case-studies/issue-2233/`](case-studies/issue-2233/README.md). `uses:` не принимает выражения, поэтому написать workflow, который сам подхватит action в день его появления, невозможно.

Замена — один шаг. Замените шаг `Open the Formal AI draft` в `.github/workflows/formal-ai-draft.yml` на шаг `uses: link-assistant/formal-ai@<tag>` и передайте ему те же входные данные, которые сегодня собирает скрипт. Всё остальное — триггер, решения о пропуске, группа concurrency, политика отказов, артефакт — не зависит от того, кто выполняет попытку. Сохраните `scripts/formal-ai-draft.lib.mjs` и его тест: решение о том, _делать ли_ попытку, принадлежит Hive Mind, а не action.
