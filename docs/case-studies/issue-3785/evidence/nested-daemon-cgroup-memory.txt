Nested box-dind daemon: peer --memory refused by a threaded cgroup v2 parent
=============================================================================

CI run at 24d6198f3 (run 41387363844, job docker-pr-check 125122749567)
------------------------------------------------------------------------
Host-daemon variant: every mounted gate and the full capability lifecycle
gate pass. Nested (--privileged box-dind) variant: task-backing and tool-data
projection pass for every tool, then the first peer launch with a memory cap
fails before any process starts:

  nested: agent: installed directory projection preserves atomic replacements, ...
  Error: Command failed: docker exec ... /verify-mounted-codex-auth.mjs "$(command -v hive)"
  Error: Command failed: docker run --detach --pull never --network none --read-only
    --cap-drop ALL --security-opt no-new-privileges --pids-limit 32
    --ulimit data=536870912:536870912 ... --memory 134217728 ...
  docker: Error response from daemon: failed to create task for container:
    ... runc create failed: unable to start container process: unable to apply
    cgroup configuration: cannot enter cgroupv2 "/sys/fs/cgroup/docker" with
    domain controllers -- it is in threaded mode

(Container IDs removed; no credential or account data is involved: the gate
was still in synthetic launch setup.)

Root cause
----------
The box-dind entrypoint (link-foundation/box ubuntu/24.04/dind) starts dockerd
without moby's cgroup v2 nesting step (moving root-cgroup processes into a leaf
cgroup and enabling subtree_control). runc therefore finds the nested daemon's
/sys/fs/cgroup/docker parent in threaded mode and refuses domain controllers
such as memory. The same limit was already recorded for --cpus in
docs/case-studies/issue-2801/README.md. The development workspace daemon used
for local runs shows the identical refusal.

Production impact
-----------------
None at launch: production never passes --memory to docker run. Configured
container limits are applied afterwards with `docker update`
(src/container-resource-limits.lib.mjs buildDockerUpdateArgs), and Router
memory arguments come only from the operator's HIVE_MIND_ROUTER_EXTRA_ARGS.
The --memory flag was a gate-only safety bound for synthetic peers.

Gate change
-----------
scripts/mounted-native-runtime.lib.mjs peerMemoryArgs() starts one disposable,
network-less, read-only, capability-free probe container with --memory on the
selected daemon. If the daemon accepts it, peers keep --memory. If and only if
runc reports the delegated-cgroup refusal above, the gate prints an explicit
INFO line and peers rely on their finite --ulimit data (already set for every
peer) plus --pids-limit. Any other probe failure stays fatal. The codex-auth,
claude-auth, claude-history and claude-refresh gates use the helper; the
self-contained Gemini storage fixture carries the same inline probe.
