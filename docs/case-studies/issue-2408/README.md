# Issue 2408: misleading reporting of out-of-memory recovery

A `/claude https://github.com/link-foundation/meta-language/pull/196 --think high` task ran for about 17 hours on 2026-10-01 and 2026-10-02 and hit out-of-memory (OOM) events twice. While the automatic recovery was **still running**, the Telegram task message said "❌ Work session failed (exit code: 1)" and `/queue` showed only the recovery session's 5h 31m. After the second OOM, the pull request got **thirteen** comments within six minutes: two "🚨 Solution Draft Failed" reports, then six pairs of "📎 Intermediate working-session log" plus kill notice. One of those notices ended with the resume command `[object Object]`.

This case study reconstructs what happened from the logs, lists each requirement of the issue, and maps every root cause to a fix and a test. The fixes are in [PR #2409](https://github.com/link-assistant/hive-mind/pull/2409), and the regression tests are in [`tests/issue-2408-oom-recovery-reporting.test.mjs`](../../../tests/issue-2408-oom-recovery-reporting.test.mjs).

## Root causes and fixes

### 1. Overlapping monitor ticks completed one exit several times

`monitorSessions` runs on a 30 s `setInterval`. `setInterval` does not wait for an `async` callback, so a tick that is still uploading a 100 MB log is overlapped by the next tick (see [Research](#research)). Every tick saw the session as still tracked and ran its own completion. The first one spent the recovery budget, and the later ones found it empty and reported "failed", overwriting the correct message. This happened 3× at 07:11 and 6× at 13:47.

**Fix:** a per-session `sessionsInFlight` guard in `src/session-monitor.lib.mjs`. A tick skips a session whose completion is still running, and logs `[VERBOSE] Session … is still being handled by an earlier monitor tick; skipping it this tick`. There is also an idempotency latch: once `killRecoverySessionId` is set, a repeated completion returns `already-recovered` instead of launching or reporting again.
**Tests:** "overlapping monitor ticks recover a killed session once and report it once" and "a repeated completion for an already-recovered session does not start another one".

### 2. An ordinary exit 1 with the sticky OOM flag was read as a kill

The first poll after an exit often comes before start-command writes the log footer. The status then has `oomKilled=true`, a dead backend and exit 1, and `resolveOomKilledState` classified that as "terminal oom-killed" (`killed=true`). A process killed by the OOM killer exits 137, not 1.

**Fix:** in `src/session-monitor.oom.lib.mjs`, only exit 137 (or a missing exit code) with a dead backend is a kill. Exit 1 with the flag is an OOM _event_ during a failed session.
**Test:** "an exit 1 with the OOM flag and no footer yet is a survived OOM event, not a kill".

### 3. A deliberate solve stop spent the OOM recovery budget

At 07:08, solve stopped on its own ("Auto-restart limit reached"), 8 h after it survived the OOM event. Because of the sticky flag, issue #2301's rule ("exit ≠ 0 after an OOM event ⇒ resume") applied, and the run consumed the only recovery attempt.

**Fix:** the new `src/session-kill-attribution.lib.mjs` reads the last 64 KB of the log for solve's own stop markers (`Auto-restart limit reached`, `Auto-resume limit reached`, `Usage limit reached - use --auto-resume-on-limit-reset`). If one is found, the exit is reported (❌, with the OOM event as a warning and the text "solve stopped on its own") but **not** recovered.
**Test:** "a deliberate solve stop after an OOM event is reported, not recovered".

### 4. A budget of 1 cannot cover a second OOM in a long run

**Fix:** `DEFAULT_SESSION_KILL_RESUME_ATTEMPTS = 3` (`--session-kill-resume-attempts`, env `HIVE_MIND_SESSION_KILL_RESUME_ATTEMPTS`). The docs are updated in all four languages.
**Test:** "a second OOM in a long run can still be recovered by default".

### 5. A SIGKILLed AI tool ended the whole solve run

At 13:37 only Claude was killed, while the container and solve kept running. `--auto-restart-until-mergeable` treated exit 137 as a tool failure and stopped. The container then exited 1 with no budget left.

**Fix:** the new `src/solve.tool-kill-resume.lib.mjs`, wired into `solve.auto-merge.lib.mjs` and `solve.watch.lib.mjs`. On exit 137 / SIGKILL it posts "⚠️ Working process killed (exit code 137, likely out of memory)" and resumes **the same Claude session in the same container and the same log**. The resume feedback asks Claude to run builds one at a time instead of in parallel subagent worktrees. It shares the `--session-kill-resume-attempts` budget.
**Test:** "a tool process killed by SIGKILL resumes its own session in-process, with a warning".

### 6. `[object Object]` as the manual resume command

`buildKillRecoveryNotice` interpolated the `{display, argv}` command object into the notice template.

**Fix:** it renders `command.display` (`src/session-kill-recovery.lib.mjs`).
**Test:** "the pull-request notice renders a resume command object, never \"[object Object]\"".

### 7. `/queue` and the headline did not cover the whole work

`/queue` used the recovery session's own `startTime`, which gave 5h 31m instead of 10h 31m + 5h 31m. The headline had no notion of "recovered".

**Fix:** recovery sessions carry `rootStartTime` and a recovery count (`session-monitor.queries.lib.mjs`, `telegram-solve-queue.helpers.lib.mjs`, `work-session-formatting.lib.mjs`). The new i18n keys `recovered` and `recoveries` exist in en/ru/hi/zh.
**Tests:** "the headline says how many automatic recoveries the work needed" and "the queue shows the total active time of recovered work and its recovery count".

### 8. The log is split across execution ids

The resource-limited session could not use start-command's same-container resume, `$ --resume <id> -- <cmd>`, because that path (`DOCKER_SNAPSHOT`) runs `docker commit` and then a `docker run` that only re-adds the stored env, volumes, mounts and networks. CPU, memory and PIDs limits are lost. Hive-mind therefore deliberately falls back to a fresh launch (`planSameContainerResume` → `container-resource-limits`), which creates a new execution UUID and a new log file.

**Mitigation here:** the recovery session records `previousExecutionUuids` (persisted in the session store), and the Telegram message shows `🆔 Execution: 88951cec (earlier logs: 0760afb4)`.
**Test:** "a fresh recovery launch keeps pointing at the earlier execution logs".
**Upstream:** [link-foundation/start#176](https://github.com/link-foundation/start/issues/176) asks start-command to (a) copy HostConfig limits into the snapshot container, and (b) accept a launch-time recovery command, so that one execution id and one appended log cover the whole work. Verified with [`experiments/issue-2408-docker-commit-drops-limits.sh`](../../../experiments/issue-2408-docker-commit-drops-limits.sh):

```
original: Memory=268435456 MemorySwap=268435456 NanoCpus=500000000 PidsLimit=64
resumed:  Memory=0 MemorySwap=0 NanoCpus=0 PidsLimit=<no value>
```

**Update — start-command 0.35.0 (start#176 part a, released 2026-10-02):** `$ --resume <id> -- <cmd>` now reads the stopped container's HostConfig (`docker inspect`, including limits set later with `docker update`) and passes memory, CPUs and PIDs to the `docker run` of the `-resume-N` container. Hive-mind pins 0.35.0 and uses it (`src/session-kill-resume.in-place.lib.mjs`):

- the installed `$` version is read from `$ --version` (`getStartCommandVersion` in `src/start-command-cli.lib.mjs`). Below 0.35.0, or when the version is unknown, the fresh launch above is kept;
- after the resume, CPU/RAM are re-asserted with `docker update` on the resumed container. A failure is logged as a warning (`Could not re-assert CPU/RAM limits …`), so a silent upstream miss is visible;
- the disk limit is enforced by hive-mind on the container's writable layer, and a snapshot starts with an empty one. The usage so far is carried as `containerFilesystemInheritedBytes` (persisted) and added to every later measurement. A disk-limited session that was never measured is not resumed in place (`container-disk-usage-unknown`), so its allowance is never silently reset.

**Tests:** [`tests/test-issue-2408-limited-in-place-resume.mjs`](../../../tests/test-issue-2408-limited-in-place-resume.mjs) (version gate, eligibility, re-assert, carried disk usage, `docker start`/relaunch modes).

### 9. Verbose output repeated on every poll

"reported oomKilled=true but its docker backend is still alive" was logged on every 30 s poll for every affected session: 10,047 lines in one bot log.

**Fix:** it is logged once per session.
**Test:** "the still-alive OOM verbose line is printed once, not on every poll".

### 10. Two failure reports from one solve run (already fixed upstream of this incident)

Comments 5953703216 (13:41:15) and 5953753740 (13:44:24) describe the same failure. The run used image `konard/hive-mind-dind:2.33.2`. The guard that recognises an earlier failure report, `isFailureAlreadyReportedOnTarget` from issue #2397, first shipped in v2.33.5.
**Test:** "the exit notifier does not post a second failure report after the loop posted one" replays this sequence against the current code.

### Audit of every restart path

After this incident every path that can start work again was rechecked:

| Path                                                      | Trigger                                                                                                                                     | Bound                                                                                      |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| solve `--auto-restart-until-mergeable`                    | CI failures, new comments, issue edits                                                                                                      | `--auto-restart-max-iterations` per solve process                                          |
| solve `--auto-resume-on-limit-reset`                      | usage limit with a reset time                                                                                                               | `--auto-resume-max-iterations`; stops with "Auto-resume limit reached" (a deliberate stop) |
| solve in-process tool-kill resume (root cause 5)          | the AI tool exits 137 / SIGKILL                                                                                                             | `--session-kill-resume-attempts` per solve run                                             |
| bot kill/OOM recovery (`src/session-kill-resume.lib.mjs`) | exit 137 / missing exit code, or exit ≠ 0 after an OOM event that is **not** a deliberate stop; never after a hive-mind resource-limit stop | `--session-kill-resume-attempts` (default 3), shared by every recovery of the root session |
| start-command `--on-kill-resume` (0.35.0)                 | **not used**: it treats the sticky flag as a kill for exit 0/1 ([start#178](https://github.com/link-foundation/start/issues/178))           | —                                                                                          |

The audit also checked the edges between these paths. Each gap found is fixed and covered by [`tests/issue-2408-restart-paths.test.mjs`](../../../tests/issue-2408-restart-paths.test.mjs), which fails on the code before the fix:

| #   | Gap                                                                                                                                                                                                                | Fix                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| B1  | The deliberate-stop check ran only for exit ≠ 0 after an OOM event. A session SIGKILLed after solve had already printed "❌ Auto-restart limit reached" (e.g. `docker stop` during the post-mortem) was recovered. | The log tail is checked for killed sessions too; the report says solve "had already stopped on its own" and nothing is restarted. |
| B2  | Exit 0 with the sticky flag and no footer yet was reported as "oom-killed" (137), which could start a recovery of finished work.                                                                                   | A terminal exit 0 is kept as success with an OOM event (`src/session-monitor.oom.lib.mjs`).                                       |
| B3  | "❌ No progress between sessions" / "identical results" and "❌ ⚠️ SUBSCRIPTION/ACCESS UNAVAILABLE" stops were not recognised as deliberate.                                                                       | Added as `no-progress` and `subscription-blocked`. "❌ AI session failed" stays recoverable on purpose (#2301).                   |
| B4  | `/stop <id>` with the root session shown in the chat did not reach the recovery session, which is tracked under a new name, so the stop was followed by another automatic recovery.                                | `markSessionStopRequested` also matches `executionUuid`, `rootSessionName` and `killRecoveryOfSession`.                           |
| B5  | When a resumed solve child (auto-continue) was killed by a signal, Node reported `code === null` and `process.exit(null)` exited **0** — a kill read as success.                                                   | `exitCodeFromChildClose` maps the signal to 128 + n (SIGKILL → 137), and the parent logs the signal.                              |
| B7  | The stop markers matched anywhere in a line, so quoted tool output (`"text":"❌ Auto-restart limit reached"`) could suppress a real recovery.                                                                      | Markers are anchored to the start of a line, allowing only `[timestamp] [LEVEL] ` log prefixes.                                   |

Logging added so the next incident can be read from the bot log alone: a `session_kill_recovery_decision` event for every killed or OOM-flagged exit (`exitCode`, `status`, `killed`, `oomEventOnly`, `deliberateStop`, `diskLimitExceeded`, `attemptRecovery`), a `session_kill_not_recovered` event with the reason when no session is started, a `[VERBOSE]` line with the policy and skip reason, and a `[VERBOSE]` line with the `$` version gate of the in-place resume.

## Research

- **Docker `State.OOMKilled` is container-wide and sticky.** moby sets it on every OOM event of the container cgroup ([`daemon/monitor.go`](https://github.com/moby/moby/blob/master/daemon/monitor.go), `case libcontainerdtypes.EventOOM: … c.State.OOMKilled = true`). It clears it only when the container starts again ([`daemon/container/state.go`](https://github.com/moby/moby/blob/master/daemon/container/state.go), `SetRunning`: `s.OOMKilled = false`). So after a child is OOM-killed, every later exit carries the flag, and the flag says nothing about why the main process exited. Some guides ([Netdata: Docker OOMKilled](https://www.netdata.cloud/guides/docker/docker-oomkilled/)) describe the older behaviour, where only an OOM-killed PID 1 set the flag. Discussion of the semantics: [moby#18510](https://github.com/moby/moby/issues/18510), [moby#38352](https://github.com/moby/moby/issues/38352) and [moby#47618](https://github.com/moby/moby/issues/47618) (the Windows variant). The exit code is the reliable per-process signal: 137 = 128 + SIGKILL.
- **`docker commit` does not keep runtime limits.** A commit captures the filesystem and image config, not the HostConfig ([docker commit reference](https://docs.docker.com/reference/cli/docker/container/commit/)). Limits set with [`docker update`](https://docs.docker.com/reference/cli/docker/container/update/) live only in the old container's HostConfig. This was verified locally (see root cause 8).
- **`setInterval` with an async callback overlaps itself.** The timer does not await the returned promise ([Node.js timers](https://nodejs.org/api/timers.html#setintervalcallback-delay-args)). The usual remedies are a re-entrancy guard or a self-rescheduling `setTimeout`. Hive-mind uses a per-session guard, so other sessions keep being polled while one completion uploads its log.
- **start-command 0.35.0 `--on-kill-resume` cannot be used yet.** Its `isKilledExit(code, oomKilled)` returns true whenever `oomKilled` is true, and the Docker-side shell condition does the same, so a container with a survived OOM event that exits 0 or 1 is "recovered". That is root cause 3 again, one layer down. Verified locally (`isKilledExit(1, "true") === true`, `isKilledExit(0, "true") === true`) and filed as [link-foundation/start#178](https://github.com/link-foundation/start/issues/178), with the fix "OOM **and** no exit code / exit 137".
- **Memory use of parallel Rust builds.** Each worktree has its own `target/` directory, so two subagents running `cargo test` compile two dependency graphs at once. `-j`/`CARGO_BUILD_JOBS` bound the parallelism ([Cargo build config](https://doc.rust-lang.org/cargo/reference/config.html#buildjobs)), and this is what the resume feedback now suggests.

## Remaining limits

- A resource-limited session needs start-command ≥ 0.35.0 to stay under one execution id and one log; with an older `$` it still gets two, and the Telegram message names both. The launch-time recovery command (start#176 part b) is not used until start#178 is fixed.
- A genuine OOM recovery runs `solve --resume` as a new solve process, so solve's `--auto-restart-max-iterations` counter starts again. The total is bounded by `--session-kill-resume-attempts` (default 3) times that limit.
- When the in-place resume falls back to `docker start` or a relaunch (rare: a command resume of an existing container is always a snapshot), the session is tracked under the execution UUID, so the container-name-based disk measurement may not find it (pre-existing since #2189).
- A real cgroup OOM could not be reproduced end to end here: the sandbox Docker has no memory controller (`docker update --memory` fails with `memory.max: no such file or directory`). The tests replay real log tails and statuses instead.
- The in-process resume (root cause 5) helps only when solve itself survives. If the OOM killer picks solve or the container's init, the bot-level recovery (root causes 1–4) is what handles it.
