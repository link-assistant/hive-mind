# Issue #2809: an OOM notice posted after "Ready to merge"

[Issue #2809](https://github.com/link-assistant/hive-mind/issues/2809) reports a pull request comment that said "ℹ️ Work session completed — an earlier container OOM event did not stop it". It was posted one second after solve had already posted "✅ Ready to merge". The OOM event behind it had happened four hours earlier. The issue sets this rule:

> The only time when OOM can be reported is just in the moment of it happening and recovery from it.

[PR #2810](https://github.com/link-assistant/hive-mind/pull/2810) changes the session monitor so that it:

- reports the OOM event on the pull request while the work session is still running;
- keeps the separate kill/restart comment for an OOM that actually stops the session;
- stops posting the after-the-fact comment for a session that completed anyway;
- adds the OOM-kill count to the Telegram completion message.

## Root cause

The monitor already detected the event in time. `resolveOomKilledState` (issue #2134) checks whether a container that reports `State.OOMKilled` is still alive. If it is, a child process was OOM-killed and the session continues. `markOomEventObserved` then stores `oomEventObservedAt` so that the event survives bot restarts, but **nothing is reported at that moment**.

Every report was produced at completion by `buildKillCompletionSections`:

- `recovered`: exit 0 after an observed event;
- `oomEventOnly`: a failed exit after an observed event, not a kill (issue #2301);
- `killed`: the session itself was killed.

`src/session-monitor.lib.mjs` posted a PR comment for all three:

```js
if (killReport.killed || killReport.recovered || killReport.oomEventOnly) {
  const notice = await announceKillOnPullRequest({ ..., recovered: killReport.recovered, ... });
```

For a successful run, solve has already posted its summary, its log and "Ready to merge" before the process exits. The monitor only learns about the exit afterwards, so the `recovered` comment always landed after "Ready to merge". The design came from issue #2134 R2: "say so in the PR". That made sense for kills and restarts. For an event the session survived, it published a stale, contradictory status. Issue #2498 had already suppressed it for merged pull requests (commit `8efbc07f`), but not for open ones like koz-3 PR #15.

A second, smaller gap: the count was available from `$ --status` (`cgroupMemory.oomKills`), and solve logged "9 process(es)". The monitor kept only the time of the first event, so Telegram could not show how many OOM kills there were.

### Why `State.OOMKilled` is an "event", not a verdict

Docker sets `State.OOMKilled` whenever an OOM event hits the container's cgroup, including when the victim is a child process. It clears the flag only when the container starts again. After a child is OOM-killed, the flag therefore stays set for the rest of the run, whatever happens to the main process. The issue #2408 case study cites the moby code ([`daemon/monitor.go`](https://github.com/moby/moby/blob/master/daemon/monitor.go), [`daemon/container/state.go`](https://github.com/moby/moby/blob/master/daemon/container/state.go)), and the semantics are discussed in [moby#18510](https://github.com/moby/moby/issues/18510), [moby#38352](https://github.com/moby/moby/issues/38352) and [moby#47618](https://github.com/moby/moby/issues/47618). A moby change (mirrored [here](https://git.causa-arcana.com/kotovalexarian-likes-github/moby--moby/commit/57d2d6ef621cc126ca904e8fc98fbacbd345790a)) describes the older behaviour: the flag was refreshed only when the container exited and was "sticky" across restarts. Some guides still describe that behaviour, or the even older one where only a PID-1 kill counted. Examples are [Netdata: Docker OOMKilled](https://www.netdata.cloud/guides/docker/docker-oomkilled/) and [Red Hat bug 1478605](https://bugzilla.redhat.com/show_bug.cgi?id=1478605). Either way, the flag cannot tell whether the work session survived. Hive Mind asks the backend and reads the exit code for that. It cannot tell how many processes died either. The kernel counter does that.

### `memory.events`: `oom` vs `oom_kill`

The cgroup v2 `memory.events` file has two counters ([kernel `cgroup-v2.rst`](https://docs.kernel.org/admin-guide/cgroup-v2.html); patch discussion: [mm/oom_kill: count global and memory cgroup oom kills](https://lkml.iu.edu/hypermail/linux/kernel/1705.3/01341.html), [add group_oom_kill memory event](https://lkml.rescloud.iu.edu/2112.0/03321.html)):

- `oom` counts how often the cgroup hit its limit and an allocation was about to fail. That can happen without anything being killed.
- `oom_kill` counts how many processes in the cgroup (hierarchically) were killed by an OOM killer.

In koz-3 PR #15 these were `oom=20` and `oom_kill=9`. The number that matches "how many times OOM happened" in the user-visible sense is `oom_kill`, which start-command reports as `cgroupMemory.oomKills`. Telegram uses that number.

## Solution

1. **In-run notice** (`announceOomEventWhileRunning`, called on each monitor tick while the session is alive, next to the recovery-lifecycle reporter):
   - It resolves the PR the same way as the existing lifecycle reporter: the started PR, the cached `resolvedPullRequestUrl`, or a linked-PR lookup for issue sessions. The lookup runs at most every 5 minutes, so a session that has not opened its PR yet does not trigger an API call on every poll.
   - It uploads the intermediate log once (`--attach-logs`), then posts the notice marked `<!-- hive-mind:oom-event-notice -->`. The marker is registered in `TOOL_GENERATED_COMMENT_MARKERS`, so solve never treats the notice as human feedback.
   - Its state (`oomEventNotice`) and the count (`oomKillCount`) are persisted, so a bot restart neither re-posts the notice nor loses the count. A failed post is retried on the next tick. A posted notice is never duplicated, even when `gh` did not print the comment URL.
   - When the live count grows, the same comment is edited, at most every 5 minutes.
2. **Completion reporting:**
   - `recovered` (exit 0): no PR comment. Telegram keeps its post-factum warning.
   - `oomEventOnly` (failed exit): a PR comment only if a restart happened (the "recovery" comment the issue asks for), or if the in-run notice could not be posted at all (for example, no PR existed while the session ran).
   - `killed`: unchanged. The kill and restart comment, with log upload, is the "recovery from it" report.
3. **A recovery session** gets a fresh `oomEventNotice`/`oomKillCount`, so an OOM in the replacement session is reported as a new event.
4. **Telegram count:** `describeKillCause` also returns `oomKillCount` from the cgroup markers. `buildKillCompletionSections` uses the maximum of that and the persisted live count, and the headline reads, for example, "⚠️ recovered from out of memory (OOM kills: 9)".

### Alternatives considered

- **Post a new comment per OOM kill.** koz-3 would have received 9 comments in four hours. That is noisy, and the 20 `oom` events would have been even worse. Rejected in favour of one comment per event, edited in place.
- **Suppress PR reporting of survived events entirely.** This contradicts R2: the issue wants the moment of the event reported.
- **Delay the completion comment until before "Ready to merge".** The monitor runs outside solve and only learns the outcome after the process exits, so it cannot be ordered before solve's own final comments. Rejected.
- **Report from inside solve.** Solve sees its own cgroup counters (it logged "9 process(es)"), but with `--isolation docker` the event is observed by the bot-side monitor. The monitor already has the PR resolution, the log upload and the kill/restart policy, so it is the single reporter.

## Other places checked (R11)

Every call that posts session-kill or OOM notices to a pull request was reviewed (`grep -rn "postKillRecoveryNotice\|announceKillOnPullRequest" src`):

- `src/session-monitor.lib.mjs`: the completion notice. **Fixed** (this defect).
- `src/session-recovery-lifecycle.lib.mjs`: the recovery-attempt lifecycle comment. It is posted while a restart is in progress, so it is already "at the moment". Unchanged.
- `src/session-monitor.oom-notice.lib.mjs`: the new in-run notice.
- The solve-side resource report ("processes killed by the OOM killer so far") went only to the solve log in koz-3. `data/koz-3-pr-15-comment-headings.json` shows no other OOM comment, and none of solve's PR comments (summary, solution log, "Ready to merge") mentions OOM. Unchanged.

## Upstream

No upstream issue was filed. Docker and the kernel behave as documented: a sticky container flag and cumulative cgroup counters. start-command (`$ --status`) already exposes `oomKilled`, `cgroupMemory.oomKills` and `oomEvents`, which is everything this fix needs. The defect was purely in when Hive Mind chose to publish.

## Tests

`tests/issue-2809-oom-reported-when-it-happens.test.mjs` drives the real `monitorSessions` loop with mocked `$ --status`, `gh` and log uploads:

- The koz-3 replay: a session with a persisted `oomEventObservedAt` of 11:13:13.140Z exits 0 with 9 OOM kills. It produces no post-factum PR comment, and Telegram shows "(OOM kills: 9)". **This test fails on the code before the fix.**
- The notice is posted once while running, with the log uploaded first when `--attach-logs` is set, and nothing more at completion.
- A growing count edits the same comment, throttled to 5 minutes. Without `--attach-logs` nothing is uploaded. Issue sessions throttle the linked-PR lookup.
- A later kill still gets its separate restart comment. A failed run is reported again only when restarted, and stays Telegram-only under `--on-session-kill=report`.
- The marker is treated as tool-generated, and the count shows only when greater than 1.

Updated tests whose expectation encoded the old behaviour: `tests/issue-2498-merged-pr-recovery.test.mjs` ("open PR survived OOM" is now Telegram-only) and `tests/test-issue-2134-killed-session-recovery.mjs` (the PR report is now in-run). The 2134 test's first monitor run previously had no PR-lookup mock and made a real `gh api graphql` call. `experiments/issue-2809-fake-gh/gh` was used to find that call, and the test now mocks the lookup.

## Known limitations

- If the first OOM event happens in the few seconds between "Ready to merge" and the process exit, the in-run notice may still land after "Ready to merge". It is still reported at the moment it is observed, not after the fact, and the window is one monitor poll.
- The count comes from the cgroup counters reported by start-command. A backend that does not report `cgroupMemory` (screen/tmux without cgroup v2 access) yields no count. The notice and Telegram then simply omit it.
