# GitHub-first competitive roadmap

The first milestone is a GitHub issue that reliably reaches a reviewable pull request after a worker handoff or a restart. The second is keeping the person who requested it informed and able to provide input. The [feature matrix](comparison.md) links every outcome to a decision here. The workstreams describe future implementation.

## GitHub owns team work

| User job                                                            | Use the existing GitHub surface                                                                           | Hive Mind responsibility                                                                                                                                                                           |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture, edit, search, prioritize, assign, and categorize team work | Issues, issue forms, labels, assignees, milestones, Projects views and custom fields.                     | Draft an issue from an authorized prompt, link to it, and make eligibility and worker selection explainable.                                                                                       |
| Organize parent, child, and blocked work                            | Native sub-issues and dependencies, including GitHub's documented relation limits.                        | Read the graph, account for pagination and permissions, and schedule only eligible work. Project fields are optional input or projections.                                                         |
| View source, history, diffs and review evidence                     | Commits, PR files, review threads, review verdicts, check logs, and Actions artifacts.                    | Prepare draft PRs, publish short run evidence with links and safe provenance, and route relevant feedback to the right attempt. Use an app-owned check for compact status where permissions allow. |
| Decide whether work can merge                                       | Rulesets, required checks and reviews, branch protection, and merge queue when configured.                | Recheck the current head, publish evidence, and use GitHub's merge mechanism under the repository's explicit policy.                                                                               |
| Read notifications and act on a phone                               | GitHub notifications and Mobile for work-item and PR actions.                                             | Send Telegram/CLI controls for pause, resume or answer and deep-link them to the affected issue, PR and attempt.                                                                                   |
| Track human-only plans                                              | Projects drafts, dates, iteration and views, plus existing calendar/reminder tools for personal routines. | Keep automation template state, leases, and attempt results where they can be recovered. Offer targeted reminders only where the pilot shows an execution need.                                    |

Use native issue/PR URLs as durable user-facing links. Keep agent transcripts, lease heartbeats, and private artifacts in execution storage with access checks. [Current GitHub capabilities](research.md#github-platform)

## W1 — Durable worker routing and handoffs

**Priority P0.** Reuse `hive` issue discovery and relation ordering, the Telegram dependency queue and execution IDs, `solve` PR preparation and review gates, and the manager's task reporting. Start with a versioned, repository-scoped worker definition in checked-in configuration. Include an enabled switch, repository/label/Projects conditions, role and prior-run outcomes, provider/model, instruction reference, execution profile, and concurrency. The reviewable definition can be drafted by an agent and activated by a human with permission. Keep an explicit CLI override and an explanation of why a rule matched, waited, or did not match.

- **Options.** Configure one process per worker today for a small pilot. Prefer a shared dispatcher with a durable ledger when multiple entry points need the same rules. Use a SQLite transaction and leases on a single host. Evaluate Postgres/Graphile Worker when multi-host dispatch needs a shared database. Evaluate Temporal if long waits and multi-service recovery justify its additional runtime. [Component trade-offs](research.md#components-and-libraries)
- **First increment.** Use an installation/repository identity plus GitHub item ID as the work key. Store versioned attempts with their role, selection reason, source event, predecessor, workspace/PR, outcome and current owner. Make launch admission idempotent across polling, manual intake, and Telegram. Support lease expiry, fencing, heartbeat, restart reconciliation and a bounded retry policy. Treat a crash between an external side effect and its recorded receipt as a reconciliation case. Look up the existing draft or check before repeating a write.
- **Second increment.** Add explicit transitions for queued, running, waiting for input, waiting for checks or review, cancelled, failed, and completed. Route implementation → review → targeted remediation on the same GitHub work item. Apply explicit success/any-outcome/fallback rules and prevent cycles. A distinct finish reason preserves “finished with no changes” and “PR ready” separately from “merged.” Report state and link to the next human action once per transition.
- **Acceptance.** Replay duplicate and out-of-order events from two channels for one test issue. The same route produces one active attempt and at most one draft PR, including a crash just after draft creation. A blocked parent waits for its child. A failed review leads to one authorized fallback. A plan explains the no-match case. With a new push, stale checks and approvals cannot release the merge gate. Verify native closing references for every required issue and preserved direct CLI/Telegram entry points.

## W2 — Sessions, context, and provider adapters

**Priority P1.** Offer an execution record with origin, who can act, provider capability, last safe event, run history and a route for answers. Start with an authorized issue/PR or Telegram command and existing session identifiers. GitHub and Telegram render a short state summary, a safe artifact index, the input requested, and the action link. Add a private reader/writer API only when this works across channels.

- **Options.** Extend existing Claude/Agent streaming and restart/resume adapters first. Evaluate an ACP adapter for provider choice and a typed capability matrix for session load, steer, pause, approval, files, context/export and model selection. A provider switch can use native resume when applicable or start a new session with a compact, user-reviewable handoff of requirements, branch/commit, changed files, test results and outstanding questions. [ACP and MCP evidence](research.md#components-and-libraries)
- **First increment.** Correlate an input with the outstanding question and task/attempt identity. Allow only authorized actors to answer once. Record visibility, expiry, attachment references and deduplication metadata. Bound and sanitize material before sending it to a different provider. Explicitly show provider fallback or unsupported actions.
- **Second increment.** Expose filtered run status and an explicit, scoped task submission interface to external scripts or approved MCP tools. Probe demand for richer composer features with attachment pointers, saved prompts and terminal links. Keep tools subject to existing execution and publication policy.
- **Acceptance.** Test native and fallback responses on two adapters, including interrupted streams and duplicate or delayed replies. A second account cannot resolve someone else's prompt or read private artifacts. A handoff opens the right branch, preserves outstanding requirements and excludes credentials, raw private context and inaccessible files. A task requiring an unsupported capability gets a visible decision.

## W3 — Schedules and event admission

**Priority P1.** Land after W1's idempotent admission. Start with a repository-owned Actions or external cron template around `hive --once` or dry-run issue preparation. Keep recurring task creation and a scheduled message into an existing session as distinct actions. Enable a template through a reviewable configuration change. [GitHub schedule and webhook constraints](research.md#g2--actions-and-webhooks)

- **Options.** Actions fits repo-scoped maintenance with default-branch rules and best-effort timing. Use a local scheduler against the durable ledger if users require timezones, explicit missed-run policy, strict duplicate prevention, or non-GitHub sessions. Add an Octokit GitHub App webhook receiver for timely events only where poll latency is a measured problem. Maintain periodic reconciliation.
- **First increment.** Define template ID, destination, schedule/timezone or event filter, skip/catch-up policy, duplicate-open rule, rate limit and enabled state. Use an occurrence ID derived from template revision and intended firing time. Reconcile issue creation by occurrence marker on retry. For webhooks, authenticate delivery, allowlist event/action/repo, deduplicate the delivery ID, acknowledge quickly and process from durable storage.
- **Acceptance.** Replay a daylight-saving transition, a missed window, disabled/re-enabled schedule, duplicate/redelivered event and open previous occurrence. Each creates at most one eligible task per window. A delayed event or inaccessible target yields a visible reason. Test a read-only preview and an authorized write in a fixture repository.

## W4 — Bot personas and memory

**Priority P2, after W1/W2 pilots.** Start with named reviewer and maintainer personas backed by repository-scoped instructions and addressed Telegram or CLI commands. Ask about one issue, get a reply with attribution, and attach delegated work to the original issue/run. Test whether users need a persistent conversation before adding state.

- **Options.** Keep team facts in reviewed repository configuration and provider-native history for a single provider. If a shared memory store is needed, use scoped records with provenance, edit/delete/export, size and expiry bounds, and explicit provider-owned mode. Untrusted run output can propose a fact for review. It cannot directly change trusted memory or raise the permission ceiling. [Memory trade-offs and upstream precedent](data/sources.md#u3--bots-and-memory)
- **Acceptance.** Two personas can act on the same issue without impersonating each other or starting reply loops. A follow-up recovers the accepted fact following a restart. Revocation removes future access. Changing provider follows the selected memory owner and surfaces what can carry over. A worker summary cannot alter team memory or create a higher-privilege worker.

## W5 — Execution operations and observability

**Priority P1.** Use `hive-manager`, current task records and recovery, Docker identifiers, Screen, Telegram and optional Router controls. Add stable correlations from an issue through attempt, host, provider and PR head. Publish summaries and provide operator views for logs, resource/queue state, model limits, and conditional retry reasons. Preserve reviewed private archives, workspace recovery and least-privilege credential boundaries. [Current operator interfaces](data/sources.md#h7--fleet-operations)

- **Options.** Begin with read-only CLI/Telegram reporting and structured events. Evaluate OpenTelemetry export for teams that already run a collector. Pilot a small authenticated, read-only run viewer behind private access if history and artifact navigation remain hard. Reuse SSH/Tailscale for private access and existing terminals locally. Grant time-limited, scoped access to sanitized artifacts only if GitHub access and existing storage are insufficient. Use existing credential mounts and provider login before adopting a secret-reference integration such as 1Password Connect. [Operations components](research.md#components-and-libraries)
- **Acceptance.** Observe queue latency, dispatch attempts, blocked status, provider wait and PR/check state in one trace for a fixture issue. Recover the trace after a task-container crash. Pause/resume keeps the correct owner and workspace. An invalid credential or quota error produces a useful reason. Raw tokens, unredacted transcripts and private artifacts remain outside public PR updates and telemetry. A disconnected viewer revokes access within its documented lifetime.
- **Host options.** Establish Linux/Docker as the reference. Validate a pinned installation, a headless provider sign-in and a remote SSH execution round trip before widening to a browser client, WSL/desktop build or multi-host lease service. VM/container isolation, disposable browser profiles and test accounts are the initial evidence environment.

## W6 — Local desktop and adjacent features

**Priority P2/P3 with evidence gates.** Preserve the fast CLI/Telegram lane and GitHub's native browsing/review UI. Start with job-only outcomes that GitHub cannot show, such as a local pre-PR patch, session view, live preview or read-only log timeline. Use Git worktrees for local patch isolation where appropriate, Playwright contexts on disposable hosts, and configured device tools only for a concrete acceptance workflow. [Workspace components](research.md#components-and-libraries)

| Decision                                               | Low-cost option                                                                                                                | Escalation trigger and acceptance                                                                                                                                                                                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Personal planner and routines                          | Adopt Projects dates/iterations and existing calendars.                                                                        | Add a worker handoff or reminder when a measured execution problem survives those integrations. Prove the reminder routes to the right owner without creating a second team board.                                                                       |
| Browser or desktop workspace, themes, voice, shortcuts | Use existing CLI/shell/GitHub/Telegram, native accessibility and dictation, plus an authenticated read-only view if warranted. | For validated needs add task-specific keyboard navigation, live preview and/or a local-only path. Test on target OSes, a keyboard and screen reader. Consider a standalone client only after proving those needs cannot be met in the existing channels. |
| Live visual or device inspection                       | Reuse worker-side Playwright, sanitised screenshot/trace output and operator diagnostics.                                      | Add an expiring view of a scoped disposable session when remote users need it. Verify session isolation, cancellation and accessible visual evidence.                                                                                                    |
| Local sessions and publishing                          | Use existing Git and provider tools to open a sandbox checkout and inspect a patch, then link publication to GitHub.           | Prototype one local-only task → patch → optional publish path if demand is confirmed. Verify restart, no duplicate PR, and no implicit cloud upload for local-only work.                                                                                 |
| Other forges and trackers                              | Keep YouTrack intake and document the GitHub contract.                                                                         | Document a requested forge's issue, PR, check, review, dependency and credential behavior. | Temporary sharing and rich outputs                     | Share GitHub-access-controlled reports and CI artifacts. | Branded mobile app or managed relay                    | Use GitHub Mobile, Telegram, SSH and private networking.                                                                       | Revisit after user tests show missed session actions on a phone where GitHub and Telegram cannot help. Validate browser-first access before taking on app-store or relay operations.                                                                     |

## W7 — Benchmark and positioning

**Run alongside W1.** Compare on user jobs with the same repository snapshots, available provider/model, starting instructions, and constraints. Use disposable fixture repos, local sandboxes and seeded CI/review events. Run a separate lane for local project chat so GitHub-oriented fixtures do not hide Up.computer's strengths. Record exact versions, host profile, tool auth mode, event timings, failures, manual workarounds, unverified paths, and cost components. [Product and measurement context](research.md#product-and-market-evidence)

| Scenario                                                                       | Record                                                                                                  | Decision rule                                                                                                                   |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Prompt or issue → linked draft PR with a passing test                          | Setup time, time to first correct draft, human actions, duplicate writes, traceability.                 | Prefer the path with fewer manual control actions after confirming equivalent output and zero duplicate publications in replay. |
| Three related issues across two repos, with an implementation → review handoff | Correct blocker and role routing, queue wait, resolution breadcrumbs, missing-context interventions.    | Require zero blocker violations or duplicate active attempts before comparing latency and interventions.                        |
| Reviewer finding and failing check after ready signal                          | Correct-head status, recovery correctness, time back to ready, stale-merge attempts.                    | Require zero unauthorized or stale merges and complete disposition of findings.                                                 |
| Worker/host restart and blocked human decision                                 | Resumed workspace and session, delivered alerts, duplicate work, abandoned jobs, and attachment access. | Require a recoverable attempt and an attributed next action. Measure p50/p95 time to recovery over repeated runs.               |
| New local project chat → parallel background task → phone follow-up            | Time to first result, setup actions, session continuity, handoff readability, and data location.        | Treat this as an independent adoption gate. Prioritize only gaps seen repeatedly with the target team.                          |
| Recurring maintenance with missed/duplicate events                             | Created tasks per window, explained skips, operator rework, GitHub write count.                         | Require idempotence under redelivery and explicit behavior for skipped windows before increasing automation coverage.           |

Measure pilot baselines before committing to numerical latency or cost claims. Segment software cost, provider spend, CI/runtime hosting and operator time. A GitHub-first workflow wins when it reliably produces actionable PRs with fewer interventions and satisfies the team's review, security and recovery requirements. Use the local lane to decide whether broader product investment is justified.
