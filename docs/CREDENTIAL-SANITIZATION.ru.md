# Санитизация учётных данных

Hive Mind считает, что сгенерированный вывод терминала, журналы, отчёты об ошибках, артефакты журналов разработки и изменения GitHub могут содержать учётные данные.

Эта мера снижает риск случайного раскрытия данных через собственные пути вывода Hive Mind. Она не делает автономного агента или подключённый к интернету хост безопасным: агент по-прежнему может получать данные и передавать их по каналам за пределами этих точек вывода. Используйте краткосрочные учётные данные с минимальными правами в изолированной среде и заменяйте любые учётные данные, которые могли быть раскрыты.

## Соглашение

Все обслуживаемые точки вывода используют санитайзер из `src/token-sanitization.lib.mjs`.

- Значения длиннее 12 символов сохраняют ровно первые и последние три символа: `abc…xyz`.
- Значения длиной не более 12 символов заменяются на `[REDACTED]`.
- Посторонний текст и структурный контекст по возможности сохраняются.
- Санитизируется каждое вхождение учётных данных, в том числе несколько значений в одной строке.
- Для stdout/stderr терминала используется буфер записей, поэтому учётные данные, разделённые между фрагментами вывода дочернего процесса, не выводятся до сканирования.
- Закодированные копии учётных данных санитизируются наравне с открытыми, и соглашение о маскировании сохраняется через кодировку. См. [Закодированные учётные данные](#закодированные-учётные-данные).
- Комментарии GitHub, тексты и заголовки PR/issue, релизы, загружаемые журналы, gist, репозиторные копии журналов разработки и данные Sentry сканируются точно на границе отправки.
- Публикация работает по принципу fail-closed. Если синхронное ядро, Secretlint или проверка остаточных совпадений завершается сбоем, внешнее изменение блокируется с ошибкой `ERR_CREDENTIAL_SANITIZATION`.
- Временные файлы публикации и локальные источники аудита доступны только владельцу (`0600`); временные каталоги загрузки имеют права `0700`.
- `--development-log` не изменяет исходные локальные журналы аудита и добавляет в индекс только санитизированные копии.

Синхронное ядро работает на [`@link-foundation/sensitive-data-sanitizer`](https://github.com/link-foundation/sensitive-data-sanitizer) (`src/sensitive-data-sanitizer.lib.mjs`) и защищает пути терминала и локальных журналов. На границах публикации затем выполняются ядро, сопоставление с известными активными токенами, Secretlint и повторное сканирование остаточных значений. Опасные параметры совместимости локального вывода не позволяют обойти границы публикации.

- Маскируются только учётные данные (`credentialsOnly`). Адреса электронной почты, идентификаторы аккаунтов и пользователей и логины GitHub остаются читаемыми ([#3724](https://github.com/link-assistant/hive-mind/issues/3724), правило 14).
- Контекст формата вокруг учётных данных остаётся читаемым, маскируются только сами учётные данные: слово схемы заголовка `Authorization` (`Authorization: token ghp…b4N`, `Authorization: CustomScheme f3a…3e5`), имя пользователя в URL, имена cookie, маркеры PEM и адреса вебхуков ([#3739](https://github.com/link-assistant/hive-mind/issues/3739)).
- Выражения оболочки, например `Authorization: token $(gh auth token)`, сохраняются: они ссылаются на учётные данные, но не содержат их.
- `HIVE_MIND_SANITIZER_DEBUG=1` включает трассировку решений санитайзера в stderr: идентификаторы правил, смещения и длины, но никогда не совпавший текст.

## Поддерживаемые формы

Правила библиотеки (форматы поставщиков, набор правил Gitleaks, контекстные ключи) вместе с дополнительными детекторами Hive Mind охватывают:

- форматы учётных данных GitHub, GitLab, OpenAI, Anthropic, AWS, Google/GCP, Azure, Slack, Discord, Telegram, Stripe, Twilio, SendGrid, npm, PyPI, Docker и распространённых систем CI;
- токены доступа/обновления OAuth, токены JWT/JWS, URL вебхуков, HTTP-заголовки Authorization и значения Cookie/Set-Cookie;
- присваивания JSON, YAML, TOML, INI, XML, переменных окружения/shell, параметры CLI, чувствительные параметры запросов, пароли строк подключения и закрытые ключи PEM;
- точные значения локальных учётных данных, которые собирает библиотека: переменные окружения с учётными данными (`knownSecretsFromEnv`), каждый токен из `hosts.yml` gh (`knownSecretsFromGitHubConfig`) и `gh auth token` (`knownSecretsFromGitHubAuth`). `KNOWN_LOCAL_TOKEN_ENV_VARS` перечисляет переменные, которые читаются всегда.

На внешних границах обнаружение намеренно консервативно. Ложное срабатывание может скрыть похожее на учётные данные значение; при сбое сканера публикация блокируется вместо отправки исходных байтов.

При анализе реализации ([#3739](https://github.com/link-assistant/hive-mind/issues/3739), [#3740](https://github.com/link-assistant/hive-mind/issues/3740)) всё обнаружение и отображение перенесено в `@link-foundation/sensitive-data-sanitizer`; собственной копии правил для учётных данных в Hive Mind больше нет. `src/sensitive-data-sanitizer.lib.mjs` добавляет только политику Hive Mind: дополнительные детекторы, исключения (имена пакетов npm [#2156](https://github.com/link-assistant/hive-mind/issues/2156), счётчики токенов [#2119](https://github.com/link-assistant/hive-mind/issues/2119), флаги конфигурации) и видимый контекст формата. Каждый обходной путь ссылается на issue в библиотеке, которое просит его поддержать (`UPSTREAM`); полный список — в [разборе случая](./case-studies/issue-3739/README.md). Secretlint остаётся независимым вторым сканером на границах публикации, а `containsKnownToken` — независимой проверкой известных значений.

## Закодированные учётные данные

Сканер шаблонов сопоставляет те байты, которые ему передали, поэтому учётные данные, попавшие в журнал только в закодированном виде, невидимы сразу для всех правил, работающих с поверхностным текстом. Это не гипотетический обход: обычные инструменты постоянно кодируют данные, не собираясь ничего скрывать, и issue [#2156](https://github.com/link-assistant/hive-mind/issues/2156) — утечка, вызванная именно этим: точка выдачи токенов реестра вернула переданные ей учётные данные обратно в кодировке base64 внутри тела JSON, оно попало в журнал, было опубликовано и отозвано сканером GitHub. Полный анализ — в [разборе случая](./case-studies/issue-2156/README.md).

Поэтому библиотека декодирует до сопоставления (`preserveEncoding`). Два обходных пути в `src/encoded-credential-detection.lib.mjs` остаются, пока библиотека их не поддерживает: base64 с переносом строк и hex коротких известных значений ([sensitive-data-sanitizer#138](https://github.com/link-foundation/sensitive-data-sanitizer/issues/138), [#140](https://github.com/link-foundation/sensitive-data-sanitizer/issues/140)):

- Ограниченные по длине последовательности base64, base64url, hex, percent-кодирования, байтовых escape-последовательностей и HTML-сущностей декодируются, и по декодированному тексту выполняются правила для открытого текста.
- Base64 читается во всех трёх вариантах выравнивания байтов, поэтому учётные данные внутри большого блока также находятся. Блоки с переносами строк сканируются как непрерывные группы строк, состоящих только из символов base64, поскольку все распространённые инструменты переносят вывод (76 столбцов для MIME, 64 для PEM), и в таком блоке нет однострочной последовательности для сопоставления.
- Замаскированное содержимое кодируется обратно, и перед подстановкой проверяется полный цикл преобразования. Подставляется только та последовательность, которая декодируется ровно в то, что предназначено к публикации; иначе вся последовательность заменяется на `[REDACTED]`. Именно это сохраняет соглашение `abc…xyz` через кодировку: `{"token":"gho_…"}` остаётся корректным base64 и декодируется в `{"token":"gho…999"}`, поэтому окружающая структура и края значения по-прежнему читаемы.
- Потоковый санитайзер удерживает завершающую группу строк, состоящих только из символов base64, пока не придёт строка, которая не может быть частью блока. Выдача таких строк по одной передавала бы санитайзеру фрагменты со сдвигом байтов. Строка, с которой блок _начинается_, тоже удерживается — на одну запись: она не состоит только из base64 и потому не входит в группу, а будучи выданной отдельно, оставляет учётные данные, пересекающие первый перенос, вне обеих частей. Обычный вывод при этом не задерживается, поскольку проверяется не длина завершающей base64-последовательности строки, а то, декодируется ли она в текст: URL, хеш коммита или дайджест содержимого — нет.
- Secretlint также выполняется по декодированному содержимому, каждая последовательность сканируется отдельно, с помощью собственного декодера Hive Mind (`findDecodableRuns`), поэтому он не зависит от декодирования в библиотеке. Избыточность между детекторами полезна тем, что их словари различаются — Secretlint знает форматы, которых нет в правилах библиотеки, — но помогает она только за декодером. На журнале из инцидента рекомендованный пресет Secretlint не находит ничего на всех 16,9 МБ; см. [сравнение библиотек](./case-studies/issue-2156/data/library-survey-output.txt).
- Исключения для пользовательского содержимого действуют на уровне поверхностного текста и намеренно останавливаются перед декодером. Они задают буквальные фрагменты, которые нужно оставить нетронутыми, а закодированная последовательность их не содержит, поэтому список исключений вызывающей стороны не может открыть брешь в этом слое. Излишняя маскировка закодированного блока стоит одной строки журнала; обратная ошибка стоит учётных данных.

Обнаружения в закодированном содержимом отдельно отражаются в подробной сводке санитизации вместе с идентификаторами сработавших правил, поэтому инцидент такого класса можно установить по журналу.

## Добавление или изменение формата

1. Проверьте формат в актуальной официальной документации поставщика по безопасности или аутентификации. Никогда не вставляйте действующие учётные данные в issue, тест, журнал или коммит.
2. Добавляйте в `tests/test-credential-sanitization-2111.mjs` только синтетические примеры. При необходимости охватывайте отдельное значение, структурированное присваивание, несколько значений в строке и разделение между фрагментами.
3. Сначала сообщите об отсутствующем формате в [`@link-foundation/sensitive-data-sanitizer`](https://github.com/link-foundation/sensitive-data-sanitizer/issues). Пока он не исправлен там, добавьте дополнительный детектор или исключение в `src/sensitive-data-sanitizer.lib.mjs` со ссылкой в `UPSTREAM` и строку в `tests/issue-3739-sensitive-data-sanitizer-migration.test.mjs`.
4. Запустите целевые тесты безопасности и набор по умолчанию:

   ```bash
   node tests/test-credential-sanitization-2111.mjs
   node tests/issue-3739-sensitive-data-sanitizer-migration.test.mjs
   node tests/test-encoded-credential-leak-2156.mjs
   node tests/test-encoded-secretlint-layer-2156.mjs
   node tests/test-require-sanitized-output-rule.mjs
   npm test
   npm run lint
   ```

5. Для новой внешней точки используйте `sanitizeForPublication`, `writeSanitizedPublicationFile` или вспомогательную функцию, которая уже вызывает их. Добавьте тест статического правила, доказывающий отклонение эквивалента без санитизации.
6. Укажите в pull request источник, тестовые случаи и компромиссы ложных срабатываний.

Проверяйте перечень поставщиков не реже одного раза в квартал и при каждом объявленном изменении аутентификации. Полезные первичные источники: [обзор аутентификации GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github), [рекомендации GitLab по токенам](https://docs.gitlab.com/security/tokens/), [идентификаторы AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html), [типы токенов Slack](https://api.slack.com/concepts/token-types), [API-ключи Stripe](https://docs.stripe.com/keys), [API-ключи Twilio](https://www.twilio.com/docs/iam/api-keys), [токены доступа npm](https://docs.npmjs.com/about-access-tokens/) и [формат отчётности PyPI о секретах](https://docs.pypi.org/api/secrets/).

## Реагирование на инцидент

Санитизация не является отзывом. Если реальные учётные данные попали в запись терминала, репозиторий, объект GitHub, загрузку, событие телеметрии или другую внешнюю систему:

1. немедленно отзовите или замените их;
2. ограничьте доступ к затронутому артефакту;
3. удалите раскрытое значение из текущего содержимого и сохранённой истории, если платформа это поддерживает;
4. проверьте журналы аудита поставщика на предмет злоупотреблений;
5. перед возобновлением публикации добавьте синтетический регрессионный тест для пропущенного формата или точки вывода.
