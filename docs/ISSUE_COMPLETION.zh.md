# 自动合并前的任务完成验证

针对任务的 solve 现在会在每次工作会话后修复拉取请求描述，并验证完成情况，无需启用 `--finalize` 或 `--ensure-all-sub-issues-addressed`。原始任务、嵌套的原生子任务，以及生成的汇总任务中的必需引用列表，都必须在描述中有肯定的关闭引用。示例、注释、标题或否定句中的引用不能证明关联。其他仓库的任务必须使用准确的仓库名称。

仓库模式会将所有未关闭任务写入汇总任务正文。GitHub 每个父任务最多允许 100 个原生子任务；其余任务仍保留在正文的必需引用列表中，属于同一个拉取请求的工作范围。

六种工具的提示都要求在当前拉取请求中完整实现并验证需求。Codex 使用 `features.goals=true`；提示要求工具通过支持的原生目标 API 设置目标，API 不可用时保留持久检查清单。完成重启循环默认最多尝试五次；`--ensure-all-sub-issues-addressed=N` 也控制此上限。尝试耗尽、用量限制或无法读取 GitHub 数据时，拉取请求保持未合并状态。

## 创建需求报告

最后一次推送后，根据当前任务描述、所有任务评论，以及三种拉取请求反馈接口生成模板：

```bash
node /path/to/hive-mind/src/issue-requirements-snapshot.mjs OWNER/REPO ISSUE_NUMBER PR_NUMBER
```

工具提示会提供已安装脚本的绝对路径。此命令只读取 GitHub 并输出模板；每条需求初始状态都是 `pending`。补充显式清单提取器未识别的文字需求。为每条需求记录可审查的实现和验证证据，仅在完成时改为 `done`。未解决的需求应保留为 `blocked`。将完整报告和生成的标记粘贴到拉取请求描述中：

```text
<!-- hive-mind:requirements:start -->
...生成的 JSON 报告...
<!-- hive-mind:requirements:end -->
```

新提交或任务、审查反馈变化后，重新生成报告。编辑描述时保留报告。关闭引用应放在报告代码块之外的描述中，每个任务分别重复肯定的关闭关键词。

## 允许合并的条件

共享合并函数检查所有自动合并入口，包括合并队列，要求：

- 完整必需任务集合的肯定关闭引用。
- 恰好一份有效需求报告，覆盖且仅覆盖该集合。
- 当前拉取请求的头提交 SHA 和当前来源摘要。
- 所有显式验收条件、`done` 状态及非空证据。
- 目标为默认分支时，GitHub 确认的原生关闭关联。

GitHub 读取、分页和响应验证必须成功。合并命令使用 `--match-head-commit` 拒绝并发代码推送。合并到非默认分支时，GitHub 不自动关闭任务；hive-mind 会在合并后明确关闭每个已验证任务，并报告各项失败。没有任务上下文的仅拉取请求维护继续使用现有合并流程。

详细模式记录已验证任务数量和提交 SHA；验证失败会指出阻塞条件。完成检查阻塞的评论会要求补齐工作和证据，而非建议手动合并。

## 验证的限制

报告是必需且及时的证据清单，不能证明任意文字需求或代理证据的真实性。人类仍需审查证据。仓库管理员可以在 hive-mind 之外通过 GitHub 合并；来源评论和拉取请求描述可能在最后读取与合并之间变化。GitHub 提供提交保护，但无法原子锁定所有外部记录。大型任务清单仍受 GitHub 正文大小和 API 限制；发布或验证失败必须阻止合并。
