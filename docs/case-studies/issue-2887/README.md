# Case study: issue #2887 — kill recovery runs the Telegram alias as the program (exit 127)

On 2026-10-09 a host-wide kill stopped four `/codex` tasks for link-assistant/router #724, #725, #727 and #728. The bot's in-place kill recovery committed each killed container and started `sh -c '/codex https://… --resume <thread>'` in the copy. `/codex` is Telegram chat syntax, not a program, so each recovered container exited at once with `sh: 1: /codex: not found` (exit 127). The bot then reported the task with the predecessor's diagnosis, `oom-killed` with exit 137, and stopped tracking it.

Runtime at the incident: hive-mind 2.34.0, start-command 0.35.4, Docker 29.6.1 with the containerd image store. The same signature recurred on hive-mind 2.35.3 / start-command 0.36.0 (2026-10-11) and on hive-mind 2.35.8 / start-command 0.37.1 (2026-10-13). It is fixed on `main` since **2.35.10** by commits `5577dc0` and `7e1d178` (issue #2630). This branch adds the exact-scenario regression tests on top of that fix, and makes the bot recover an in-place resume that dies with 126/127 instead of dropping it.

## Requirements

From the issue's "Expected" and "Suggested fix" sections:

1. R1. The in-place command is the executable (`solve …` / `hive …`) with the original arguments plus `--resume <last tool session id>`.
2. R2. The alias form (`/codex …`) appears only in user-facing text (Telegram, PR comments).
3. R3. Every place that runs a command uses the executable form: `$ --resume`, `executeWithIsolation`, any `recoveryCommand`.
4. R4. A test proves that the in-place resume command never starts with `/`.
5. R5. A resumed container is classified by its own exit: 127 is "command not found", not `oom-killed`.
6. R6. Tracking and recovery continue after such an exit instead of dropping the session.
7. R7 (from the case-study template). Collect the data, reconstruct the timeline, find each root cause, check every similar place in the codebase, and report upstream problems where relevant.

Other places that run a command were checked (R3). The fresh-run fallback in `startKillRecoverySession` uses `plan.command.binary` and `args` and was never affected. `executeWithIsolation` receives the binary and argv separately. start-command's own `recoveryCommand` (`execution-recovery.js`) is built from the argv hive-mind passes. No caller passes `chatDisplay` to a runner: `grep -rn chatDisplay src/` shows it only in the Telegram resume hint (`src/session-resume.lib.mjs`) and where `withoutResume` rebuilds it (`src/session-kill-resume.fresh-session.lib.mjs`).

## Tests

`tests/alias-recovery-2887.test.mjs` has 8 tests. The router#728 scenario uses the real `resumeKilledSessionInPlace` with a fake runner and asserts the exact command line of the verified workaround from the issue. The completion tests use the real `runKillRecoveryForCompletion`.

- Once that is confirmed, the alias parts of the open PRs #2895, #2918 and #3127 are superseded. #2896 also covers #2889 and #2890, so it is not superseded as a whole.
- The relaunch covers 126/127 only. Other "never started" signatures, such as a missing `solve` dependency that exits 1 at import time, are ordinary failures and are not relaunched.

## Related components

- start-command (`$`, link-foundation/start): `$ --resume <execution> -- <command>` runs `<command>` through `sh -c`, so any string passed there must be a shell command, not chat syntax. Since 0.37.0 a task container has a command handoff (`/.start-command-resume-<name>`), and `$ --resume` restarts it with `docker start` instead of committing it (see issue-2889).
- POSIX shell exit statuses: 127 for "command not found" and 126 for "found but not executable" ([POSIX Shell Command Language, 2.8.2](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html#tag_19_08_02)).
- `buildShellCommand` (`src/shell-command.lib.mjs`) quotes each argument, so a URL or a `--resume` value cannot be split or expanded.

## Reproduction

The original failure needs Telegram, a Docker host and a kill. The unit tests reproduce each step with fakes:

```bash
npm ci
node --test tests/alias-recovery-2887.test.mjs
```

By hand (from the issue): send `/codex https://github.com/<owner>/<repo>/issues/<n>` with Docker isolation, `docker kill` the task container while the tool runs, and wait for the kill recovery. On 2.35.8 or earlier the `<name>-resume-1` container exits 127 with `sh: 1: /codex: not found`. On this branch it runs `exec solve … --resume <id>`.
