# Case study: issue #2190 — Codex refuses to work as requested

Issue: https://github.com/link-assistant/hive-mind/issues/2190 (opened 2026-09-03T06:13:08Z by konard).
Pull request: https://github.com/link-assistant/hive-mind/pull/2227.
Evidence: everything quoted here is committed under [`data/`](data/) and listed in [`MANIFEST.md`](MANIFEST.md).

## Executive summary

Three Codex runs of `solve` between 2026-08-30 and 2026-09-02 ended with a question to the human instead of a pull request, and one of them cost 9.2 million input tokens. All three ran `solve v2.15.1 --tool codex --think xhigh` inside a Docker-isolated container whose `~/.codex` was the host's whole `~/.codex` directory, bind-mounted. That directory contained `plugins/cache/openai-curated-remote/superpowers/6.3.0`, a plugin the Codex CLI had synchronised into the host's global state from OpenAI's curated remote catalog. Codex lists installed plugin skills to the model at start, and the plugin's `using-superpowers` skill says, in capitals, that a skill must be invoked "BEFORE any response or action" and routes every "Let's build X" through `brainstorming`, which ends in "Should I proceed?". The model obeyed the plugin, not the task.

The fix has four parts, each its own commit, test and documentation:

1. **Audit and auto-repair of the global configuration** so nothing but the minimal profile (Playwright MCP) survives on the host, with Codex's remote plugin sync and Claude's marketplace auto-install turned off (`0a6c997f`).
2. **Mount split**: a task container receives only the credential files and the session directories, never the rest of `~/.claude` / `~/.codex` (`461170d2`).
3. **`--playwright-skill`** for the browser exception the issue carves out, alongside the default Playwright MCP (`07634bb5`).
4. **Router hardening** for `--use-router --isolation docker`: the sidecar binds only its internal-network address, task tokens are revoked the moment the container exits, and a guard fails the task with exit code 77 when any credential other than the router token appears (`5fa204de`).

One capability the router lacks was reported upstream as [router#545](https://github.com/link-assistant/router/issues/545); a shell workaround is in place meanwhile.

## Root causes

### RC1 — a plugin in the host's global state was mounted into every task

`--isolation docker` bind-mounted the whole `~/.codex` (and `~/.claude`, `~/.claude.json`, `~/.agents`) of the host into the container. Anything the host had accumulated — here `plugins/cache/openai-curated-remote/superpowers/6.3.0` — became part of every task's Codex home. Codex advertises installed plugin skills in the model's context, which is why the model's very first action in all three runs was to read `using-superpowers/SKILL.md`.

This is fixed structurally by R6: the plugin cache is now per container and comes from the image.

### RC2 — Codex syncs a remote plugin catalog into the global state on every start

`codex_core_plugins::manager: completed remote installed plugin bundle sync` appears in each log. With `features.remote_plugin` enabled (the default in Codex 0.15x), the CLI keeps the curated remote catalog materialised under `plugins/cache/openai-curated-remote`. Nothing in Hive Mind asked for superpowers; the catalog put it there. R2 turns the sync off (`-c features.remote_plugin=false`) and the audit removes what is already present.

### RC3 — the `using-superpowers` skill overrides the task instructions

`data/upstream/superpowers-using-superpowers-SKILL.md`: "Invoke relevant or requested skills BEFORE any response or action — including clarifying questions, exploring the codebase, or checking files", "IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE", and the routing rule "'Let's build X' → superpowers:brainstorming first". `brainstorming/SKILL.md` ends its flow by presenting a design and waiting for approval. For an unattended `solve` run there is no one to approve, so the run ends with a question. This is exactly the shape of all three refusals, including the one on formal-ai#1070 that ignored an explicit instruction.

### RC4 — the token inflation

The three runs report 656 515, 910 232 and 9 241 801 input tokens with long-context pricing in each. Two effects stack: the skill files (63 + 250 + 171 lines, plus `writing-plans`) are read into context at the start, and the brainstorming flow makes the model survey the repository broadly before it may act (the formal-ai run spent 27 minutes and 120 tool calls producing a summary). Neither the system prompt nor the issue changed between the earlier, cheaper runs and these; the mounted plugin did.

### RC5 — router gaps

Reviewing the router path against the issue's security wording found three gaps, all now closed:

- The sidecar bound `0.0.0.0` and was attached to `bridge` for upstream access, so any container on `bridge` could reach it. The router has no way to bind by network alias (`--host` takes only an IP; `data/upstream/router-README.md`), hence the sh entrypoint wrapper and router#545.
- Token revocation happened only on the normal release path; a `solve` process killed with its container left the token valid until its 24 h / 5000-request limits.
- Nothing watched the credential files inside a routed container, so a task could log in with an OAuth account or point `model_provider` elsewhere without being stopped.

Alternatives considered and rejected:

- **Filtering the plugin cache instead of not mounting it.** Would have to track every future Codex/Claude layout change; the mount split removes the class of problem.
- **Editing the system prompt to say "ignore installed skills".** Excluded by the issue (R1), and it would not fix the token cost.
- **`inotify` for the auth guard.** Inotify does not fire for bind-mounted files written from another mount namespace in all configurations, and Claude Code rewrites files in place; a 1 s poll is deterministic and cheap.
- **`iptables` inside the sidecar.** Needs `NET_ADMIN`; binding the right address needs nothing.

## Online facts used

- Codex CLI documentation now points to `developers.openai.com/codex/{auth,config-basic,config-reference,skills}`; the in-repo docs are stubs (`data/upstream/codex-docs-*.md`). The auth storage implementation is `codex-rs/login/src/auth/storage.rs` (`data/upstream/storage-login.rs`): `auth.json` holds either `OPENAI_API_KEY` or `tokens.{id_token,access_token,refresh_token}` and is rewritten in place.
- Superpowers 6.3.0 skill texts (`data/upstream/superpowers-*-SKILL.md`) as shipped in the curated remote catalog.
- Router `0.125.4` README (`data/upstream/router-README.md`): `--host` / `ROUTER_HOST` default `0.0.0.0`, no alias binding; open and closed issues at capture time (`data/upstream/router-issues.txt`, 544 entries) contain no request for it.
- Docker: an `--internal` network has no gateway and no masquerade; `docker network connect` can be applied to a running container and does not affect existing listening sockets.
- `@playwright/cli` 0.1.19: `playwright-cli --help` prints its `Agent skill: <path>` hint only when `CLAUDECODE` or `COPILOT_CLI` is set (`playwright-core/lib/tools/cli-client/program.js`). The first image build of `--playwright-skill` grepped for that line and failed in CI (run 34202031772, `docker-pr-check`) because the build has neither variable; the skill is now located by path under the global npm root (`@playwright/cli/skills/playwright-cli`), with the env-gated hint only as a fallback. `playwright-cli install --skills` was rejected as the locator: it also initialises a `.playwright/` workspace, tries to provision a browser, and writes to `~/.cache/ms-playwright`.
