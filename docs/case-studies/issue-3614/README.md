# Case study: issue #3614 — the bot polls Docker and session state up to ~95 times a minute

- Issue: https://github.com/link-assistant/hive-mind/issues/3614
- Pull request: https://github.com/link-assistant/hive-mind/pull/3615
- Reported on: hive-mind 2.39.2, start-command 0.37.8, a 6-CPU host with 2–3 docker-isolated tasks (2026-10-20)
- Upstream report (start-command's own monitor loop): https://github.com/link-foundation/start/issues/238

## What was measured

| Window (UTC)      | Bot's child processes | Bot's own code | Processes started per minute                                                                                                                                  |
| ----------------- | --------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 20:03:31–20:03:46 | 0.52 cores            | 0.02 cores     | `docker inspect -f {{.Id}}` 87, `docker inspect -f {{.State.Running}}` 75                                                                                     |
| 20:20:56–20:21:01 | 0.99 cores            | 0.10 cores     | `sh -l -c '…/$'` 95, `bun $ --status <session>` 95, `docker inspect -f {{.State.Running}}` 71, `sh -l -c docker` 59, `sh -c pgrep -l` 47, `sh -l -c which` 47 |

## Root causes

1. **No shared result per session.** The session monitor (every 30 s), the queue consumer's processing count (`canStartCommand` → `getExternalProcessingSnapshot`, several times per loop while items wait), `/limits`, `/queue`, `/log` and `/terminal_watch` (every 2.5 s per watch) each ran their own `$ --status <session>`. `isSessionRunning()` could run it twice for the same session.
2. **Every `$` call was two login shells.** command-stream's `$` wraps each command in `/bin/sh -l -c`, and `findStartCommandBinary()` ran `` $`which $` `` before every start-command call without caching it. So one status check was `sh -l -c which $` + `sh -l -c $ --status …` + the `bun` process + its own `docker inspect`.
3. **One process per container per caller.** Backend liveness ran `docker inspect` (through `sh -l -c`) per container, `screen -ls` per session, and `pgrep -l -x <tool>` (through `sh -c`) once per tool.
4. **Overlapping timers.** The session monitor, `/top`, the bidirectional-interactive pollers and the Formal AI / router sidecar maintenance used `setInterval(asyncTick)`. A slow Docker daemon made ticks pile up, each starting its own processes.
5. **Outside hive-mind:** start-command's detached monitor for each docker-isolated task samples cgroup memory every second (`CGROUP_SAMPLE_INTERVAL_SECONDS = 1` in `src/lib/cgroup-memory.js` of start-command 0.37.8), running `docker inspect -f {{.State.Running}}` and, when the local cgroup is unreadable, `{{.HostConfig.CgroupnsMode}}` each round. That is the 36–47 checks per minute per task in the issue. Reported upstream as link-foundation/start#238; hive-mind cannot change that loop.

## What changed

- **`src/status-check-cache.lib.mjs`** — one in-memory cache shared by the whole bot. A key is checked at most once per `HIVE_MIND_DOCKER_STATUS_MIN_INTERVAL_MS` (default **5000 ms**, so at most **12 checks per minute** per container or session; bot option `--docker-status-min-interval-ms`). Callers that arrive while a check runs await the same promise. The interval counts from when a check finished. Failures are not cached. `invalidate()` / `invalidateSessionStatus()` drop an entry when the bot itself starts or stops a task; a check that was already running when it was invalidated answers its callers but is not stored. `0` disables the reuse and keeps the de-duplication.
- **`src/status-probes.lib.mjs`** — `runProbe()` runs `docker`, `screen`, `tmux`, `pgrep` and `$` with `execFile` (no shell, with a timeout; a missing binary is exit 127). Docker liveness for all containers comes from one cached `docker ps`, screen liveness from one cached `screen -ls`.
- **`src/start-command-cli.lib.mjs`** — `findStartCommandBinary()` resolves `$` from `PATH` once (no `which` process) and caches it; `$ --status` / `$ --list` run through `runProbe()`.
- **`src/isolation-runner.lib.mjs`** — `querySessionStatus()` and `listIsolationSessions()` read the shared cache (callers get a copy); `isSessionRunning()` and the backend probes reuse it; launching and stopping a session invalidate it; container exists / writable-layer size probes run `docker` directly; `checkTmuxSessionRunning()` now reads tmux's exit code (it used to report a missing session as running).
- **`src/telegram-solve-queue.helpers.lib.mjs`** — `getRunningProcesses()` answers every tool from one cached `pgrep -l -x claude|codex|…` run without a shell.
- **`src/serial-poller.lib.mjs`** — `startSerialPoller()` schedules the next tick with `setTimeout` only after the current one settled. Used by the session monitor (with a per-session budget so one slow completion does not hold up the others), `/top` and the bidirectional-interactive pollers. The sidecar maintenance timer skips a tick while the previous one runs.
- **`src/version-info.lib.mjs`** — `/version` answers share one `getVersionInfo()` result for 30 s instead of starting ~66 shell commands per message.
- **Lint** — `hive-mind/no-login-shell-probe` flags `$`-template probes (`docker`, `which`, `screen`, `tmux`, `pgrep`, `ps`, start-command) on bot paths, which run through `sh -l -c`; `hive-mind/no-overlapping-interval` flags `setInterval` with an async callback. Existing call sites are listed with reasons in `eslint-rules/baselines/`, so only new ones fail. The #3206 sync-I/O rules (`hive-sync-ok`) still block new sync calls on bot paths.

## Verification

Automated tests (all in the default suite):

| Test                                      | What it shows                                                                                                                                                                                                                                      |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tests/status-check-cache-3614.test.mjs`  | Default 5000 ms (12/min) with no configuration; the env variable and the bot option override it; concurrent callers share one check; 95 lookups/min start ≤12 checks per resource (≤4 at 15 s); invalidation, failures and copies behave as above. |
| `tests/status-probes-3614.test.mjs`       | With stub binaries on `PATH` counting processes: concurrent `querySessionStatus()` / `isSessionRunning()` run `$ --status` once; no `which`; one `docker ps` / `screen -ls` / `pgrep` for all; no shell; launch/stop invalidate.                   |
| `tests/serial-poller-3614.test.mjs`       | Ticks never overlap; failed ticks keep the poller alive; sidecar maintenance skips overlapping ticks; one slow session does not hold up the monitor.                                                                                               |
| `tests/version-info-shared-3614.test.mjs` | Concurrent `/version` requests share one run; a failed run is not reused.                                                                                                                                                                          |
| `tests/polling-lint-rules-3614.test.mjs`  | The two new ESLint rules accept and reject the intended code.                                                                                                                                                                                      |

Load replay: `node experiments/issue-3614-load-simulation.mjs [minIntervalMs]` tracks 3 docker sessions and has four callers (status query, `isSessionRunning`, backend probe, `pgrep`) ask about each session 95 times per minute, with stub binaries counting processes. Time is scaled by 20 (one minute = 3 s). Result on this branch:

```
min interval 5000 ms: $ --status per task 10/min, docker ps 10/min, pgrep 10/min, which 0/min, total 50/min
min interval 15000 ms: $ --status per task 4/min,  docker ps 4/min,  pgrep 4/min,  which 0/min, total 20/min
```

The same replay against `main` started 28 `$ --status` per task, 42 `docker`, 42 `pgrep` (168 counted processes) in the same time — and that excludes the `sh -l -c` / `sh -c` wrappers and the real `which` processes, which the stubs do not count. On `main` the count is bounded only by how fast the host can start processes.

Not verified here: the CPU numbers on the reporter's host. The acceptance criterion's cgroup measurement needs the production deployment; the replay above and the tests show the per-task check count it depends on. start-command's own 1 s loop (row 30) stays until link-foundation/start#238 is fixed upstream.
