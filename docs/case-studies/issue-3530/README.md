## Root causes

1. **Three comments per kill (R1).** The kill notice, the intermediate log upload and the auto-updated lifecycle comment were written by three independent paths, each with its own copy of the session details.
2. **"Mess after it" (R2, R4).** The lifecycle reporter (#2498/#2630) posted and kept editing a GitHub comment for every phase, and a kill recovery started like a fresh session, so the start comment could not say it was a recovery or which attempt it was.
3. **Recoveries at the worst moment (R3).** A recovery was launched after a fixed delay, without the queue's resource checks, so after a mass kill every task restarted at once.
4. **Two solves for one task (R5, #3532).** After the in-place resume, the session was tracked under the execution UUID, and liveness was probed with `docker inspect <execution UUID>`. The container is named after the session, so the probe failed, a healthy run was declared dead with "exit 1", and a fresh restart was started next to it. Nothing checked for a running container of the same task, or another session for the same URL, before launching. Secondary: a queued `/solve` was checked for duplicates only when it was queued, not when it launched.
5. **Wrong cause (R6, #3533).** The kill classifier trusted the sticky `State.OOMKilled` flag, which stays true after a survived child OOM kill, and did not know the host had rebooted (Docker exit 255).
6. **Four ids per task (R7).** The bot chose a session name, start-command created a separate execution UUID, and every fresh relaunch added one more of each. The AI tool's session id was a fifth, unrelated id.
7. **Split logs (R9).** A fresh relaunch is a new start-command execution with its own log. start-command has no way to link it to the earlier one, and reusing the earlier id truncates the earlier log ([start#229](https://github.com/link-foundation/start/issues/229)).

## Solutions and why

- **One kill notice with a pending note.** The notice is posted once, before the recovery decision. With `--attach-logs` it heads the log comment, so there is one comment instead of two. Once the decision is known, the marked "auto recovery is pending" block is edited away, or replaced with the reason there is no recovery. This follows the issue's suggestion exactly and keeps GitHub to two comments per kill (the notice, and the next start).
- **Telegram-only lifecycle.** Waiting, launching, running and attempt `n/m` are shown in the bot's message, which is already edited in place.
- **Resource gate on the task queue.** The recovery calls the same `canStartCommand` checks a queued task does, and needs them to pass several times in a row, so it waits for memory to be freed _and stable_.
- **Container identity and duplicate guards (#3532).** The container name is tracked separately from the execution UUID. Before a launch, the bot refuses if any container of the task family runs or another tracked session for the same URL works.
- **No promise that cannot be kept.** The pending note is posted only when a recovery can be planned (policy, attempts left, a resumable session); otherwise the final notice is posted once the decision is known. Settling the note is retried, a lost comment id is found again by the notice's marker, and if the note still cannot be edited and no recovery started, one short follow-up comment says why. "Pending" is never the last word on GitHub.
- **Closing the launch windows (#3532).** A recovery between its duplicate check and its tracking is marked as launching (for up to 10 minutes), so `/solve` and another recovery for the same URL see it as busy. A direct `/solve` that is being launched counts as a sibling too. A tracked sibling counts only while its container still runs, and an unknown state counts as running. Under the queue's `one_at_a_time` strategy a recovery waits while a task of the same tool is processing, as a queued task does.
- **Boot identity (#3533).** `/proc/sys/kernel/random/boot_id` changes on every boot. A changed id with no orderly-stop record means a hard reset, which is reported once for all tasks. A heartbeat or stop that comes before the comparison is not recorded, so it cannot hide the previous run's state, and every write uses its own temp file.
- **One id.** `--session U --session-id U` makes start-command's session, execution, log file and container the same UUID. The bot passes U to solve as `HIVE_MIND_TASK_SESSION_ID`, because start-command does not export it ([start#230](https://github.com/link-foundation/start/issues/230)), and solve passes `--session-id U` to Claude Code for the first fresh session. Only a `solve` launch owns the id: `hive` runs many solves, which must not share it. A second fresh Claude session in the same task, or an id that already has a transcript, keeps its own id, because Claude Code refuses to reuse one.
- **Whole log via `/log`.** start-command cannot alias or link executions yet ([start#231](https://github.com/link-foundation/start/issues/231)), so hive-mind keeps the chain itself. Every recovery's track event already stores `rootSessionName`, `killRecoveryOfSession` and `previousExecutionUuids`; `buildSessionLogChains` joins them (union-find), and `/log` uploads `<latest>-all-attempts.log`, with a header per attempt. Over the 50 MB Telegram limit it falls back to the requested attempt and says so.

## Online research

- Claude Code documents `--session-id` as a CLI flag that sets the conversation's UUID ([CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-reference)). Locally, 2.1.303 lists it in `claude --help`.
- Codex has several requests for a caller-chosen session id on `exec`. [#25111](https://github.com/openai/codex/issues/25111) was closed as not planned, [#15271](https://github.com/openai/codex/issues/15271) as a duplicate, and [#7801](https://github.com/openai/codex/issues/7801) is open. Hive-mind's use case was added there ([comment](https://github.com/openai/codex/issues/7801#issuecomment-6264516362)), instead of opening another duplicate.
- start-command: [start#176](https://github.com/link-foundation/start/issues/176) (closed) asked for one UUID and one log across OOM recovery; `$ --resume` keeps the execution, its resource limits and its log, and [start#187](https://github.com/link-foundation/start/issues/187) added the attempt log boundary. `sessionNameHistory` (introduced with [start#162](https://github.com/link-foundation/start/issues/162), per the comment in `lib/execution-store.js`) keeps the names a resume assigns, but a caller cannot add one.

## Limits and what is left upstream

- **Different ids after a fresh relaunch.** Until start#229/#231 are fixed, a fresh relaunch (when in-place `--resume` is impossible) gets a new UUID. Telegram shows only the latest one, and `/log` on any of them returns every attempt.
- **Codex.** Codex sessions cannot take the task id until openai/codex#7801 is delivered.
- **No lock across hosts.** The duplicate guards live in the bot (monitor + queue), which covers every launch the bot makes. A `solve` started by hand outside the bot for a task the bot is already running is not detected. A solve-level lock across containers would need shared state between containers and is not implemented.
