# Issue #4190 — Golden-ratio defaults for solve queue admission

The reciprocal of the golden ratio is `(sqrt(5) - 1) / 2`, or approximately `0.61803398875`. The issue specifies **61.8%**, so Hive Mind stores `0.618` and starts applying each queue strategy at that exact boundary. A full resource still has **38.2 percentage points** of nominal headroom when a check first triggers. The baseline had eight admission checks spread across three defaults. Each metric was resolved twice, once for a structured entry used by admission and once for a legacy field used by the display. Whole-number rounding in the RAM, disk, and GitHub samples could move the effective comparison for a fractional threshold. Provider usage was also floored before the limits display checked whether to show its warning. ### Effects of the new threshold

- RAM, CPU, disk, and the two five-hour windows start applying their strategies 3.2 percentage points earlier. As an example, a 100 GiB disk has 38.2 GiB of nominal space left at the new threshold, up from 35 GiB. The separate minimum-free-space requirement still matters on small filesystems.
- The Claude and Codex weekly checks allow only one task of the affected tool at a time from 61.8%, 35.2 percentage points earlier. An idle tool can still start a task. This reduces the amount of parallel work that can consume the remaining weekly budget. A busy tool can spend more time with work waiting in the queue.
- The GitHub gate starts 11.8 percentage points later. On a 5,000-request primary quota it applies at 3,090 requests, leaving 1,910, compared with 2,500 under the previous default. The check is consulted when the same tool already has running work. Secondary limits and calls from other processes can add pressure below the primary threshold. The existing reset/retry path still handles quota errors, and busy deployments can opt into the prior 50% default with `HIVE_MIND_GITHUB_API_THRESHOLD=0.5`. [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Prior GitHub limit investigation](../issue-1726/README.md)
- These are admission margins on observed snapshots. A task can consume additional resources after it starts, and CPU uses five-minute load per logical CPU. The threshold alone cannot establish workload-specific safety or predict a provider's reset. Startup pacing, per-task constraints, and rate-limit retries still handle distinct conditions.

## Existing components and alternatives

- Hive Mind already has a threshold resolver, a Links Notation parser, a limit cache, and a task-start reservation. These components cover metric-specific strategies, precedence, and admission ordering. Adding decimal percentage inputs to the existing parser gives a per-metric Links Notation entry the same precision as an individual ratio override. [Configuration](../../../src/queue-config.lib.mjs), [Throttling](../../../src/telegram-solve-queue.throttling.lib.mjs), [Start reservation](../../../src/queue-start-reservation.lib.mjs)
- [p-queue](https://github.com/sindresorhus/p-queue) offers process-local concurrency and interval limits. [BullMQ](https://docs.bullmq.io/guide/queues/global-concurrency) offers a global concurrency limit across workers. Either would still require Hive Mind's host measurements, provider-window checks, and per-metric strategies. The native queue can apply the default without an additional dependency or migration.
- Google's SRE guidance describes using CPU rate, load average, and other task-specific utilization signals for overload decisions. Kubernetes also uses distinct memory and filesystem signals and configurable minimum reclaim amounts for pressure eviction. Both examples support selecting measurements and margins based on the action and workload. The golden ratio is the shared policy specified here. [Google SRE, Handling Overload](https://sre.google/sre-book/handling-overload/#utilization-signals-LEsGs7), [Kubernetes node-pressure eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)

## Reproducing the boundary

Run `node --test tests/queue-thresholds-4190.test.mjs`. The suite exercises the production throttling functions using cached samples and synthetic provider auth fixtures. The original defaults fail all eight cases. The implemented policy passes all eight, including the 3,089/5,000 and 3,090/5,000 GitHub examples and decimal override precedence. The test is discovered by the default CI suite.
