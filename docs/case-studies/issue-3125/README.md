## Root causes

### RC1. No AI tool except Codex was told about the memory limit or how many build jobs fit

`src/codex.prompts.lib.mjs` told Codex about container resources (#2838). Claude, OpenCode, Agent, Qwen and Gemini got nothing. Claude wrote `cmake --build … --parallel` with no number. For the Makefile generator, CMake turns that into `gmake -j`, which has no job limit. `CMAKE_BUILD_PARALLEL_LEVEL` does not cap it either, because CMake reads that variable only when neither `--parallel` nor `-j` is given. Verified with CMake 3.28 ([experiment](../../../experiments/issue-3125/cmake-parallel-jobs.sh), [log](logs/cmake-parallel-jobs.log)):

```
--parallel (no number)                 … gmake -f Makefile -j
--parallel, CMAKE_BUILD_PARALLEL_LEVEL=2 … gmake -f Makefile -j
no flag, CMAKE_BUILD_PARALLEL_LEVEL=2  … gmake -f Makefile -j2
--parallel 2                           … gmake -f Makefile -j2
```

Each `cc1plus` for a GoogleTest suite takes several hundred MB. On 6 CPUs, an unlimited `make -j` fills 2.92 GiB.

### RC2. The killed tool's build kept running and a second OOM kill ended solve

`logProcessesSurvivingSession` (#2395) only listed leftover processes, and only with `--verbose`. The build Claude started survived Claude's death. 32 s later it triggered a second OOM kill, and the kernel chose solve (`node-MainThread`). solve could not finish its own work: commit the uncommitted work, report, or exit with its own code. The issue lists 10 uncommitted files left in the container.

### RC3. All processes had `oom_score_adj` 0, so the OOM killer picked the AI tool

The kernel kills the process with the highest badness, which is roughly its RSS plus swap and page tables, plus `oom_score_adj` × allowed memory / 1000. With everything at 0, `claude` (≈358 MB RSS) was the largest single process and lost, while the many smaller `cc1plus` jobs that caused the pressure lived on. Nothing told the kernel that the build is the cheap thing to kill. Raising another process's `oom_score_adj` needs no privilege when the uid is the same. Children forked later inherit the value. Only lowering it below 0 needs `CAP_SYS_RESOURCE` ([experiment](../../../experiments/issue-3125/oom-score-adj-permissions.sh), [log](logs/oom-score-adj-permissions.log)).

### RC4. In-place resume ran the Telegram alias `/claude` as the program

`session-resume.lib.mjs` built the resume command from the bot's display form (`/claude <url> …`), and the snapshot ran it through `sh -c`, which gave `sh: 1: /claude: not found`, exit 127. This is the same defect as #2887 (`/codex: not found`), still present for in-place docker-snapshot resumes.

### RC5. The box-dind entrypoint keeps stale daemon pid files in snapshot containers (upstream)

`docker commit` keeps `/var/run`, so the snapshot contains the old `/var/run/docker/containerd/containerd.pid` (pid 57). In the new container pid 57 belongs to another process. containerd refuses to overwrite its pid file and the nested dockerd shuts down. `start_dockerd()` in `ubuntu/24.04/dind/dind-entrypoint.sh` (link-foundation/box) does not clear stale pid files. This did not cause exit 127, but every in-place resume of a dind task loses Docker.

### RC6. The memory preflight measured the host, not the container

`memory-check.mjs` read `/proc/meminfo`, which shows the host inside a container, and reported `10220MB available, swap: 4095MB` with 2.92 GiB and no swap really available. The log contradicted itself: the resource line next to it showed `233 MB used of 2.9 GB limit`, and anyone reading the preflight, including the AI tool, got the wrong budget.

With these changes, the incident would most likely go like this:

1. Claude is told to build with at most 2 jobs.
2. If it still runs an unlimited build, the kernel kills a `cc1plus` instead of `claude`.
3. If `claude` is still killed, solve stops the leftover build and survives to commit, report and exit with its own code.
4. A recovery runs the real CLI.

### Alternatives considered

- **Cap jobs through the environment** (`MAKEFLAGS=-j2`, `CMAKE_BUILD_PARALLEL_LEVEL`, `CARGO_BUILD_JOBS`). An explicit `-j`/`--parallel` on the command line overrides these, and that is exactly what happened here. The env vars would also change the jobs of every repository's own scripts. The prompt rule plus the OOM preference cover the case the env vars cannot.
- **A per-command memory cgroup** (`systemd-run --scope -p MemoryMax=…`) or `ulimit -v`. There is no systemd in the task container, and creating cgroups inside it needs delegation the container does not have. `ulimit -v` limits virtual memory, which breaks JITs and sanitizers that reserve large address ranges.
- **A user-space OOM daemon** (earlyoom, nohang, systemd-oomd). These watch host-wide memory and act on PSI or free memory, not on one container's `memory.max`. They would need to be installed in the image and configured per limit. `oom_score_adj` uses the kernel's own killer and needs no extra process.
- **Lower solve's and the tool's `oom_score_adj` instead of raising the builds'.** Going below 0 needs `CAP_SYS_RESOURCE`, which the task user does not have.

## Remaining limits

- The guard polls once a second, so a build that fills memory in under a second can still win. Its children that are forked after the raise inherit 500.
- `oom_score_adj` only changes **which** process dies. A build that needs more than the limit still fails, and the prompt asks the tool to retry with fewer jobs.
- The post-mortem `oom_kill` counter (1) disagreed with the kernel journal (2 kills). It was probably read before the second kill; this PR does not change start-command's post-mortem.
- RC5 needs the box fix. Until then, an in-place resume of a dind task starts without a working nested Docker daemon.
- `tests/playwright-mcp-prompts.test.mjs` has 4 failures that also happen on the base commit; they are unrelated to this change.
