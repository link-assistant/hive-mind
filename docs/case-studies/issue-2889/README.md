# Case study: issue #2889 — concurrent kill-recovery snapshots fill the disk

After a host-wide kill, the bot recovered four killed Rust tasks in place at about the same time. Each recovery ran `$ --resume` in `docker-snapshot` mode, which is a `docker commit` of the whole writable layer of the stopped task container. The four layers were 11, 21.2, 23.5 and 36.8 GiB, almost all of it Cargo `target/` output, on a host with 52 GB free. The commits ran together for more than 30 minutes, containerd used about 280 % CPU, free disk fell to 2 GB, and two commits failed with `no space left on device`. Each successful snapshot then kept a full copy next to the original container, and nothing removed either.

Runtime at the incident: Ubuntu 24.04 (6 CPU, 11.7 GB RAM, 193 GB disk), Docker 29.6.1 with the containerd image store (`overlayfs` snapshotter), hive-mind 2.34.0, start-command 0.35.4. Hive-mind now pins start-command 0.37.8, which already has the copy-free `docker start` resume (start#198, released in 0.37.0).

## Requirements

From the issue's "Expected" and "Suggested fix" sections:

1. R1. Avoid the copy: resume the task container with `docker start` (`ResumeMode.DOCKER_START`, no commit), with the replacement command read from a file in the container.
2. R2. If a snapshot is needed, check free disk against the writable-layer size first, with headroom for the compressed blob and the unpacked snapshot.
3. R3. Run snapshots one at a time.
4. R4. Drop regenerable caches first (Cargo `target/`, `node_modules/.cache`, …) or exclude them, without ever touching the source tree.
5. R5. Once a snapshot-derived container has started, remove the original stopped container.
6. R6. Remove obsolete `start-command-resume/*` images after the task finishes.
7. R7. Report the state in Telegram (`waiting for disk`, `snapshotting 12/37 GiB`) instead of failing silently.
8. Expected: recovery never fills the disk it needs, and does not duplicate tens of GB of regenerable build output.
9. From the case-study template: collect the data, reconstruct the timeline, find each root cause, check similar places, and describe upstream problems with reproducible examples (here as text only: see "Upstream issue text").

## Experiments

All three ran on Docker 29 with `rhysd/actionlint:1.7.12` as a small image that has `sh`. Each script prints every Docker command it runs, and the `.log` next to it is its output.

1. `01-prune-prototype.py` (+ `01-prune-prototype.sh`): a gated container with a fake Cargo `target/` and `node_modules/.cache` is killed and started again. The gate holds it idle, and the prune script removes both caches. `SizeRw` falls from 15,215,147 to 3 bytes, the commit succeeds, and `src/main.rs` is still in the image.
2. `02-command-handoff.py`: start-command's handoff argv. After `docker kill`, a command file is copied in with `docker cp` and `docker start` runs it in the same container: `REPLACEMENT-RAN`, the original files are still there, PID 1 is the new command, and it starts in 2.6 s with no commit.
3. `03-prune-module.mjs`: the real `inspectDockerTaskLaunch` and `pruneStoppedContainerCaches` from this branch on a fail-closed container. `SizeRw` falls from 35,000,076 to 32 bytes. Two directories are pruned; `Cargo.toml` and `src/` are kept, and the task ran only once (`TASK-RAN`). With the gate already open, the module refuses to prune.

## What remains

- **Legacy containers with a timed gate** (tasks without resource limits, started before start-command 0.37) are snapshotted without pruning. Starting them would run the original task once the 30 s gate times out. Containers started from now on have the handoff, so this case goes away as old containers are removed.
- **`HIVE_MIND_KEEP_TASK_CONTAINER=always`** does not stop the removal of a replaced original. Its files are in the image and the `-resume-N` container, so nothing is lost, but the original's name is no longer inspectable.
- **Images stay while their container is kept** (keep policy `always`, or `on-failure` after a failure). That is intended: `docker start -ai` of a kept container needs its image.
- **The queue is per bot process.** Two bots on one host, or a manual `$ --resume`, are not serialized by hive-mind. start-command's own snapshot lock then refuses after 1 s (see upstream text a).
- **Only the Docker data root is measured.** `checkDockerDiskSpace` runs `df` on `DockerRootDir`. start-command's preflight also checks a separate containerd root; hive-mind's guard does not. When the bot talks to the host daemon through its socket, `df` measures the bot container's filesystem, not the host's (issue #3001, open PR #3003).
- **The live layer size is not re-measured.** The guard uses the monitor's last measurement before the kill, because `docker inspect --size` can take minutes. Anything written between that measurement and the kill is not counted.
- **The earlier PRs** #2894 (same scope, unmerged) and the snapshot parts of #2896 overlap this branch; the maintainer should pick one.

## Upstream issue: link-foundation/start#224

Filed as https://github.com/link-foundation/start/issues/224 on 2026-10-15. The text below is what was filed.

The `docker start` resume itself needs nothing more from start-command: 0.37.0 added it (start#198, start PR #204), and hive-mind now relies on it. The following would let hive-mind delete code or close the remaining gaps. Evidence is from start-command 0.37.8, `src/lib/`.

> **Title:** Docker snapshot resume: wait for the snapshot lock, configurable original removal, image cleanup for callers, and progress
>
> 1. **Wait for the snapshot lock.** `acquireSnapshotLock` (`docker-snapshot-safety.js` L11-L44) calls `lock.acquire(1000)` and then throws "A Docker snapshot resume is in progress on this host. Retry after it finishes." Two concurrent `$ --resume` calls in `docker-snapshot` mode therefore fail instead of running one after the other. Reproduce (expected from the code, not run here): kill two task containers without a command handoff and run `$ --resume <a> -- sh -c true & $ --resume <b> -- sh -c true`; the second fails within a second. Suggestion: `--snapshot-wait <seconds>` (or `START_SNAPSHOT_LOCK_WAIT`) that waits on the lock, printing "waiting for snapshot of <name>" once.
> 2. **Wait for disk instead of refusing.** `preflightSnapshot` (L76-L140) refuses when free space is below 2 × `SizeRw` + 10 GiB. A caller that knows other snapshots are finishing must re-run the whole resume. Suggestion: an optional wait with a timeout, like 1, and an exit code that callers can tell apart (for example 75, `EX_TEMPFAIL`).
> 3. **A startup window for `--remove-original`.** `execution-resume.js` L664-L683 checks `State.Running` once, right after the replacement's `docker create` and `docker start`. A replacement that dies a second later has already cost the original. Suggestion: `--remove-original-after <seconds>`, which removes the original only if the replacement is still running after that delay. Hive-mind would then drop `removeReplacedResumeOriginal`.
> 4. **Image cleanup for callers that remove containers themselves.** The `start-command.snapshot-image` label is removed only by start-command's own completion watcher (`snapshotImageCleanupSnippet`, `docker-cleanup.js` L365). Suggestion: document the label as a stable interface, or add `$ --cleanup <execution>`, which removes the container and the images it was derived from without force.
> 5. **Progress during the commit.** `docker commit` prints nothing until it finishes, and with the containerd image store it takes 10+ minutes even for small layers. Suggestion: write elapsed-time lines (every minute) to the execution log during a commit, so callers can report "snapshotting, 12 min" honestly.
> 6. **A size hint for the preflight.** `docker inspect --size` walks the whole layer and can take minutes for tens of GB. Suggestion: `--snapshot-size-hint <bytes>` for callers that already measured the layer.
> 7. (Low priority) **A pre-commit hook** for containers without a handoff, for example `--snapshot-prepare <command>` run with `docker exec` after a safe `docker start`, so callers like hive-mind do not need their own prune step.
>
> Workaround today: serialize snapshots in the caller, check disk before calling `$ --resume`, and remove the original and the images in the caller, as hive-mind does in `src/kill-recovery-snapshot-guard.lib.mjs` and `src/kill-recovery-snapshot-cleanup.lib.mjs`.

## Related components

- start-command 0.37 command handoff and `ResumeMode.DOCKER_START` (`docker-command-handoff.js`, `execution-resume.js`); `docker-runtime-args.js` L139 enables it for every detached container.
- The Cache Directory Tagging specification (`CACHEDIR.TAG`, signature `8a477f597d28d172789f06886806bc55`): <https://bford.info/cachedir/>. Cargo writes it into `target/`, which is what makes the Cargo case safe to detect.
- `docker commit` has no exclude option ([docs](https://docs.docker.com/reference/cli/docker/container/commit/)). `docker cp` works on stopped containers ([docs](https://docs.docker.com/reference/cli/docker/container/cp/)). `docker image rm` without `--force` refuses images in use ([docs](https://docs.docker.com/reference/cli/docker/image/rm/)).
- The containerd image store ([Docker docs](https://docs.docker.com/engine/storage/containerd/)). The issue attributes the 10+ minute commits of small layers to its diff computation, which walks the whole mounted filesystem.
- `disk-space-saviour` (link-foundation) cleans disks in general. It caused the incident's dockerd OOM through concurrent `docker diff` calls (its issue #22), so it is not a fit for per-container pruning.
