# Issue 3831: productive task time exhausted a transient-outage budget

The linked run already recognized Codex's capacity error and resumed the same session three times. It stopped at the fourth capacity failure because the retry budget counted **42 hours 24 minutes since the first failure**, including long periods of successful work, against a 12-hour outage limit. The missing recovery transition, rather than missing recognition of this exact message, explains the incident.

The fix gives each continuous outage its own bounded retry window. Genuine provider progress resets the outage clock, consecutive backoff, and capacity-fallback counter. All six execution adapters use the shared recovery observer. Initialization, heartbeat events, synthetic API errors, and tool-result prose cannot replenish the budget.

## Causes and implementation plan

| Cause                                                                                            | Implementation                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createTransientRetryBudget` starts on the first retry and never observes recovery               | Add `recordProgress()`, which ends the previous outage and clears granted-attempt accounting. Keep the time/count backstops for uninterrupted failure.                                                                                     |
| Per-adapter `retryCount` and `argv._capacityRetryCount` survive productive recovery              | A shared observer resets both when a trustworthy provider event arrives after a granted retry. A later outage starts at the first backoff rather than inheriting old delays or premature model fallback.                                   |
| The same lifecycle exists in six execution adapters                                              | Wire the observer into each adapter's parsed event stream. Codex and Qwen only accept protocol stdout; their stderr JSON is diagnostic telemetry. Agent and OpenCode retain their existing support for structured stdout/stderr records.   |
| Codex, Agent, OpenCode, Qwen and Gemini transport exceptions bypass the stream/exit retry blocks | Reuse the `retryTransientFailure` policy for Codex stream/exit/catch and every other affected catch path. Keep the observed session available in catch; preserve authentication-error handling.                                            |
| Gemini logs preservation but does not set the next invocation's resume argument                  | Set `argv.resume` from the captured session before a transient retry.                                                                                                                                                                      |
| OpenCode leaves its session variable null throughout streaming                                   | Capture supported session-ID fields from parsed events and initialize from an explicitly resumed session. Existing command construction already supports `--session`.                                                                      |
| Some documented transient signatures miss the classifier                                         | Recognize contextual HTTP 529, Claude high-load/no-response text, timeout/rate/server error names and Codex response-stream failure variants. Retain permanent subscription/auth/model/quota behavior and contextual HTTP-number matching. |

Recovery is deliberately based on work, not on a new process starting. Codex accepts completed successful commands/tools/file changes and substantive assistant/reasoning items. Claude and Qwen accept substantive assistant blocks or tool calls, excluding API error messages. Agent/OpenCode accept substantive text/tool-use records. Gemini accepts assistant message content. A result event merely quoting an error is not a recovery signal and never restarts an otherwise successful run.

The retry policy remains bounded and configurable: general transient backoff starts at three minutes and caps at thirty minutes; capacity backoff starts at 15 seconds and doubles up to four minutes, with five same-model retries before the existing fallback policy. A model switch keeps its existing fast retry delay. Request timeouts retain their separate settings. The default outage budget is twelve hours, with count caps as runaway backstops. This fix changes when a recovered outage ends, not the configured waiting policy.

## Research and existing components

Sources below were checked against the archived primary-source documents and related issue discussions. Reports corroborate symptoms; they do not independently establish this run's root cause.

- [OpenAI API error documentation](https://developers.openai.com/api/docs/guides/error-codes) identifies `503` with `server_is_overloaded` as temporary model overload and recommends waiting before retrying, respecting `Retry-After`. This distinguishes infrastructure capacity from billing or credential errors. Snapshot: `data/openai-errors.md`.
- [Claude API errors](https://platform.claude.com/docs/en/api/errors) documents rate limiting, internal errors, overload, and errors that can arrive after a streaming response starts. The wrapper therefore needs both stream-event and process-exit handling. Snapshot: `data/claude-api-errors.md`.
- [Claude Code error documentation](https://code.claude.com/docs/en/errors) explains its own finite request retries and limits on retrying partial responses. It also documents bare 529, model high load and no-response errors. Native retries do not guarantee a completed CLI task; the outer session resume remains necessary. Snapshot: `data/claude-code-errors.md`.
- [Codex 57128](https://github.com/openai/codex/issues/57128) and [57414](https://github.com/openai/codex/issues/57414) describe long inactivity gaps after the same error with later successful resume. Their UI lifecycle hypotheses are distinct from this CLI wrapper's measured budget defect. Full bodies/comments are archived.
- [Codex 22390](https://github.com/openai/codex/issues/22390) is the existing retained-state capacity-retry tracker. [PR 31058](https://github.com/openai/codex/pull/31058) proposes a separate bounded capacity retry policy, preserving completed work and avoiding transport fallback for capacity. It was **open and unmerged** at research time, so its behavior cannot be assumed available in the incident CLI. Its supplied screenshot shows a reconnect countdown, not verification of this Hive Mind fix; the downloaded JPEG is retained in `data/`.
- [Claude Code 35771](https://github.com/anthropics/claude-code/issues/35771) contains overload/retry reports; its closure is inactivity-based, not evidence that every retry path is fixed. [49013](https://github.com/anthropics/claude-code/issues/49013) requests configurable fallback and was closed as a duplicate. Hive Mind already distinguishes overload retry from explicit capacity fallback and retains that distinction.
- Recent relevant Hive Mind work includes [PR 2854](https://github.com/link-assistant/hive-mind/pull/2854) (observed-model fallback), [2040](https://github.com/link-assistant/hive-mind/pull/2040) (five same-model capacity retries and fallback order), [2104](https://github.com/link-assistant/hive-mind/pull/2104) (safe Codex high-demand resume), and [1950](https://github.com/link-assistant/hive-mind/pull/1950) (same-model overload retry). The shared planner is reused so those policies survive this fix.

## Practical limits

No client can ensure that a remote service recovers before a configured bound. A continuous outage still stops when the explicit budget/count limit is reached, with the existing preserved session and resume information. Genuine work starts a fresh outage window; initialization alone cannot keep the task retrying forever. No unsupported claim is made that underlying Codex UI recovery, a pending upstream PR, or provider capacity itself is fixed by this repository change.
