# Лучшие практики обновления зависимостей для разработки с использованием AI (languages: [en](DEPENDENCY-UPDATE-BEST-PRACTICES.md) • [zh](DEPENDENCY-UPDATE-BEST-PRACTICES.zh.md) • [hi](DEPENDENCY-UPDATE-BEST-PRACTICES.hi.md) • ru)

Этот документ описывает, как привести все зависимости репозитория — на всех используемых в нём языках — к последним версиям и как поддерживать их в этом состоянии. Именно на него ссылается каждая задача, создаваемая командой `fix <repository-url> --update-all-dependencies`, и подсказка `--update-all-dependencies`, которую добавляют `solve`, `hive` и Telegram-бот, поэтому описанные ниже практики — это именно те практики, которым просят следовать AI-решатель.

## Почему обновление зависимостей важно для разработки с AI

Устаревшее дерево зависимостей обходится дороже, чем те уязвимости, о которых все говорят:

1. **Модель работает с устаревшим API.** AI-решатель пишет код под ту версию, которую находит установленной. Четыре года зафиксированных версий означают четыре года обходных решений, которые в текущем релизе уже не нужны.
2. **Накапливается самописный код.** Почти каждый «маленький хелпер» в зрелом репозитории появился потому, что у зависимости _на тот момент_ не было такой возможности. Обычно сейчас она есть.
3. **Уязвимости копятся молча.** `dependency-review-action` проверяет только те зависимости, которые _изменяет_ pull request. Уязвимость, опубликованная для пакета, зафиксированного год назад, для неё невидима навсегда (см. [Проверяйте то дерево, которое вы действительно поставляете](#9-проверяйте-то-дерево-которое-вы-действительно-поставляете)).
4. **Отставание становится неисправимым.** Шесть мажорных версий позади — это не в шесть раз больше работы, чем одна: руководства по миграции предполагают, что вы пришли с предыдущего релиза.

Обновить всё сразу и осознанно дешевле, чем не обновлять ничего, пока что-нибудь не заставит.

## Что означает «все зависимости»

«Все» — буквально. Зависимость — это всё, что сборка получает извне репозитория:

| Категория                         | Примеры                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------ |
| Зависимости времени выполнения    | `dependencies`, `[dependencies]`, `require`, `install_requires`                |
| Зависимости для разработки        | тест-раннеры, линтеры, форматтеры, проверки типов, плагины сборки              |
| Транзитивные записи в lock-файлах | `package-lock.json`, `Cargo.lock`, `uv.lock`, `composer.lock`, `Gemfile.lock`  |
| Базовые образы                    | каждый `FROM` в каждом `Dockerfile`, `docker-compose.yml`, `devcontainer.json` |
| Действия CI/CD                    | каждый `uses:` в `.github/workflows/*.yml` и в составных `action.yml`          |
| Тулчейны и версии языка           | `engines`, `rust-version`, директива `go`, `TargetFramework`, `.nvmrc`         |
| Инфраструктурные модули           | модули и провайдеры Terraform, зависимости Helm-чартов, подмодули git          |
| Хуки pre-commit                   | ревизии в `.pre-commit-config.yaml`                                            |

Если номер версии где-то записан в репозитории — он входит в область работ.

## Команды обновления по экосистемам

Команда по умолчанию у большинства пакетных менеджеров намеренно остаётся **внутри** ограничений, уже записанных в манифесте, и поэтому никогда не пересекает мажорную версию. В правой колонке — команда, которая действительно переписывает ограничения. Каждая проверена по документации самого инструмента; ссылки собраны в [`docs/case-studies/issue-2184/data/ecosystem-update-commands.json`](./case-studies/issue-2184/data/ecosystem-update-commands.json).

| Экосистема            | Остаётся внутри ограничений      | Обновляет до последней версии, пересекая мажоры                                   |
| --------------------- | -------------------------------- | --------------------------------------------------------------------------------- |
| JavaScript/TypeScript | `npm update`                     | `npx npm-check-updates -u && npm install`                                         |
| Python                | `pip install -U`                 | `uv lock --upgrade` • `pip-compile --upgrade` • `poetry update`                   |
| Rust                  | `cargo update`                   | `cargo upgrade --incompatible && cargo update` (cargo-edit)                       |
| Go                    | —                                | `go get -u ./... && go mod tidy`                                                  |
| C#/.NET               | `dotnet list package --outdated` | `dotnet outdated -u` (dotnet-outdated)                                            |
| Java/Kotlin/Scala     | `./gradlew dependencyUpdates`    | `mvn versions:use-latest-releases versions:update-properties`                     |
| PHP                   | `composer update`                | `composer require vendor/pkg:^X`, затем `composer update --with-all-dependencies` |
| Ruby                  | `bundle update`                  | `bundle update --all` после повышения ограничений в Gemfile                       |
| Elixir/Erlang         | `mix deps.update --all`          | правка `mix.exs`, затем `mix deps.update --all`                                   |
| Dart/Flutter          | `dart pub upgrade`               | `dart pub upgrade --major-versions`                                               |
| Swift                 | `swift package update`           | правка требований в `Package.swift`, затем `swift package update`                 |
| Haskell               | `cabal outdated`                 | `cabal update` • `stack upgrade --resolver latest`                                |
| GitHub Actions        | —                                | поднять каждый `uses:` до нового релиза (тег или закреплённый digest)             |
| Docker                | —                                | поднять каждый тег `FROM` и заново закрепить digest                               |
| Инфраструктура        | —                                | `terraform init -upgrade` • `helm dependency update` • `pre-commit autoupdate`    |

В этой таблице спрятаны три ловушки:

- **`npm update` никогда не пересекает мажор.** Он разрешает версии внутри диапазонов `^`/`~` из `package.json`. Только `npm-check-updates -u` переписывает сами диапазоны; `--target latest` — его поведение по умолчанию.
- **`cargo update --breaking` доступен только в nightly** (`-Z unstable-options`). На стабильном канале пересечение мажора — это `cargo upgrade --incompatible` из `cargo-edit`.
- **Maven фиксирует версии в `<properties>`.** Один только `versions:use-latest-releases` оставляет все версии из свойств позади — запускайте `versions:update-properties` в том же вызове.

## Ключевые принципы

### 1. Сначала таблица, потом изменения

Для каждой экосистемы перечислите все зависимости с версией, зафиксированной сегодня, и версией, выпущенной сегодня, **получая её из реестра, а не по памяти**. У обучающих данных модели есть дата отсечки, у реестра — нет. Используйте `npm view <pkg> version`, `cargo search`, `pip index versions`, `gh release list` или эквивалент вашей экосистемы.

Именно таблица делает результат пригодным для ревью: читатель сразу видит, что сдвинулось, что нет и что было пропущено.

### 2. У всего, что осталось позади, должна быть записанная причина

Зависимость, оставшаяся на старой версии, — это решение, а решения фиксируются: баг апстрима со ссылкой, снятая с поддержки платформа, платный тариф, peer-зависимость, которая ещё не догнала. Молчание неотличимо от недосмотра, и следующий человек потратит час, чтобы выяснить это заново.

### 3. Пересекайте мажорные версии осознанно

Для каждого мажорного обновления: прочитайте changelog и руководство по миграции, адаптируйте код под новый API и удалите прослойки, которые были нужны старой версии.

**Ослабленное ограничение или пропущенный тест ради «прохождения» мажора — это не обновление.** Два антипаттерна, за которыми стоит следить:

```diff
- "some-lib": "^3.0.0"
+ "some-lib": "*"          # не обновление: диапазон, скрывающий проблему
```

```diff
- it('serialises nested nodes', () => { ... })
+ it.skip('serialises nested nodes', () => { ... })   # не обновление: удалённый сигнал
```

### 4. Используйте новые возможности и удаляйте самописные аналоги

Это принцип с наибольшей отдачей и тот, который чаще всего пропускают. Если в новой версии появилось то, что репозиторий реализует вручную, удалите локальную копию и используйте возможность апстрима. Конкретно:

- локальный хелпер `deepMerge`/`retry`/`debounce`, который библиотека теперь экспортирует,
- полифил платформенного API, который есть в новой базовой версии среды выполнения,
- собственный парсер CLI, который теперь покрывает фреймворк,
- самодельный кэш, появившийся в клиентской библиотеке.

**После обновления дублирующегося кода и логики должно стать меньше, чем было.** Если в диффе меняются только номера версий, обновление не доведено до конца.

### 5. Сделайте ограничения честными

- **Поднимите нижние границы**, которые на годы отстают от того, что действительно установлено. Граница `>=1.0` при `4.2` в lock-файле означает, что CI и свежий `pip install` тестируют разные деревья.
- **Уберите верхние границы**, исключающие текущий релиз. `<5`, написанное, когда актуальной была `4`, — это ограничение, которого никто не выбирал.
- **Перегенерируйте и закоммитьте все lock-файлы.** Обновлённый манифест со старым lock-файлом — это репозиторий, где результат CI и установка у потребителя расходятся.

### 6. Одна версия зависимости на весь репозиторий

Если одна и та же зависимость зафиксирована в нескольких местах — в нескольких языковых реализациях одного протокола, в `Dockerfile`, в workflow, во фрагменте документации — приведите все закрепления к одной версии. Репозиторий, который фиксирует одну библиотеку в четырёх разных версиях, имеет четыре разных поведения и тестирует только одно.

### 7. Обновляйте тулчейн, а не только пакеты

Версия языка — это зависимость:

- `engines.node` / `.nvmrc` / `node-version` в `actions/setup-node@v5`
- `rust-version` и `edition` в `Cargo.toml`
- директива `go` в `go.mod`
- `TargetFramework` в `*.csproj` и `global.json`
- `maven.compiler.source`/`target`, версия Gradle wrapper
- `requires-python` в `pyproject.toml`

Мажорная версия тестового SDK или библиотеки утверждений обычно двигается вместе с тулчейном, поэтому обновляйте их в том же проходе.

### 8. Зелёный CI и ноль новых предупреждений об устаревании

Запустите полный набор сборки, тестов и линтинга для **каждой** экосистемы после обновления — а не только для той, которую вы правили последней, — и добейтесь зелёного CI. Затем устраните предупреждения об устаревании, которые внесло обновление. Предупреждение, оставленное сегодня, — это ломающее изменение, которое заблокирует следующее обновление.

### 9. Проверяйте то дерево, которое вы действительно поставляете

После обновления проверьте уязвимости получившегося дерева:

```bash
npm audit --package-lock-only --audit-level=high   # JavaScript/TypeScript
cargo audit                                        # Rust
pip-audit                                          # Python
bundle audit                                       # Ruby
dotnet list package --vulnerable                   # C#/.NET
govulncheck ./...                                  # Go
```

`--package-lock-only` важен: он проверяет lock-файл **в том виде, в каком он закоммичен**, поэтому результат — это то, что получит потребитель, и его нельзя сделать зелёным разрешением версий, которое происходит только на этом раннере. Поставьте аналогичную задачу на расписание: только запуск по расписанию способен заметить уязвимость, опубликованную после того, как код перестал меняться. Сама задача workflow описана в [Лучших практиках CI/CD](./CI-CD-BEST-PRACTICES.ru.md).

### 10. Сообщайте о блокерах в апстрим

Когда обновление заблокировано багом в зависимости, откройте задачу в её репозитории на GitHub с воспроизводимым примером, применённым здесь обходным решением и предложением исправления в виде кода — и сошлитесь на этот отчёт из работы, вместо того чтобы молча откатить версию. Закрепление со ссылкой — это отслеживаемое решение; закрепление без ссылки — навсегда.

## Как поддерживать актуальность автоматически

Обновиться один раз и остановиться — значит через год получить тот же самый бэклог. Настройте автообновление, чтобы следующее отставание приходило как pull request, а не как ещё одна задача.

### Dependabot

Dependabot принимает 33 значения `package-ecosystem`, покрывающих все экосистемы из таблицы выше, кроме Haskell. Нужна одна запись `updates:` **на экосистему и на каталог** — монорепозиторию с тремя `package.json` нужны три записи `npm`.

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    groups:
      all-dependencies:
        patterns: ['*']
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
  - package-ecosystem: docker
    directory: /
    schedule:
      interval: weekly
```

Основную работу делают две настройки:

- **`groups`** объединяет десятки pull request'ов по одной зависимости в один, благодаря чему и стоимость CI, и стоимость ревью остаются ограниченными.
- **`open-pull-requests-limit`** (по умолчанию 5) молча перестаёт открывать pull request'ы по достижении лимита — если кажется, что Dependabot остановился, обычно причина в этом.

Учтите, что сам по себе Dependabot не выполнит работу из принципов 3 и 4: он поднимает версию и на этом останавливается. Он не даёт накапливаться мелкому отставанию, но не мигрирует API и не удаляет прослойки.

### Renovate

[Renovate](https://github.com/renovatebot/renovate) покрывает более широкий набор менеджеров и может быть развёрнут на собственной инфраструктуре (self-hosted). Его `rangeStrategy: bump` и пресеты группировки решают ту же задачу, что и конфигурация выше; выберите один инструмент и настройте его как следует, вместо того чтобы запускать оба.

## Автоматическое обновление зависимостей

Ничего из этого не нужно делать вручную. Команда `fix` автоматизирует весь процесс — ровно так же, как `fix --ci-cd` делает это для пайплайнов:

```bash
fix https://github.com/owner/repo --update-all-dependencies
```

Эта команда:

1. **Определяет языки репозитория** через API GitHub Linguist (`GET /repos/{owner}/{repo}/languages`), упорядочивая их по количеству байт на язык.
2. **Получает дерево файлов ветки по умолчанию** (`GET /repos/{owner}/{repo}/git/trees/{branch}?recursive=1`) и находит все закоммиченные манифесты и lock-файлы, пропуская вендорные каталоги вроде `node_modules/`, `vendor/`, `.venv/` и `target/`.
3. **Сопоставляет оба сигнала с пакетными экосистемами.** Любой из них по отдельности ошибочен: Linguist не видит экосистемы без собственного исходного кода (GitHub Actions, Docker, Terraform), а манифесты не видят язык, чей манифест необычен или отсутствует.
4. **Создаёт задачу на сопровождение**, перечисляющую каждую найденную экосистему с обнаруженными манифестами, lock-файлами для перегенерации, командой, которая пересекает там мажоры, подсказкой по настройке Dependabot и стандартной подсказкой, построенной по принципам выше. Задача создаётся с типом **Task** и меткой `dependencies`.
5. **Передаёт задачу в `/solve --development-log --deep-analysis --auto-merge --update-all-dependencies`**, который итерирует до тех пор, пока обновление не будет влито. Каждая опция, которую `fix` не потребляет сам (например `--tool`, `--model`, `--think`), передаётся в `/solve`.

Используйте `--dry-run`, чтобы посмотреть задачу без её создания, и `--no-solve`, чтобы создать задачу без запуска `/solve`:

```bash
fix owner/repo --update-all-dependencies --dry-run
fix owner/repo --update-all-dependencies --no-solve
```

### Почему это Task и что из подсказки исключается

`/solve --deep-analysis` выдаёт указания про первопричину и отладочный вывод **только для задач типа Bug**, а у обновления зависимостей нет первопричины, которую нужно искать. Создание задачи с типом `Task` выбирает не-баговый вариант этой подсказки — исследование, покрытие требований, планирование решения, — и именно он здесь полезен. Типы задач настраиваются на уровне организации, а метки — на уровне репозитория, поэтому если целевой репозиторий не принимает ни того, ни другого, задача всё равно будет создана без них.

`--deep-analysis` также содержит указание сообщать в апстрим из [принципа 10](#10-сообщайте-о-блокерах-в-апстрим), поэтому `fix` исключает этот абзац из тела задачи, чтобы не выдавать его дважды. Все остальные абзацы выдаются безусловно.

## Опция `--update-all-dependencies`

Та же подсказка доступна как опция в каждой команде, запускающей решатель, и по умолчанию выключена:

```bash
solve https://github.com/owner/repo/issues/123 --update-all-dependencies
hive https://github.com/owner/repo --update-all-dependencies
```

В Telegram-боте флаг принимается в том же виде в командах `/solve`, `/hive`, `/fix` и `/task`.

Включение опции добавляет в системную подсказку решателя раздел про обновление зависимостей, поэтому работа, о которой просит задача, выполняется **вместе** с приведением всех зависимостей к актуальным версиям, а не поверх устаревшего дерева. По умолчанию она выключена, потому что незапрошенная миграция зависимостей внутри несвязанного исправления бага делает pull request непроверяемым: включайте её, когда обновление — часть того, что вам нужно, или используйте `fix --update-all-dependencies`, когда оно и есть цель.

Поддерживается для `--tool claude`, `--tool codex`, `--tool opencode`, `--tool agent`, `--tool qwen` и `--tool gemini`.
