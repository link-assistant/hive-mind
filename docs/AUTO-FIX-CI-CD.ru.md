# Автоматическое исправление CI/CD после слияния

Используйте `--auto-fix-ci-cd` вместе с `--auto-merge`, чтобы продолжать исправлять CI/CD после слияния pull request:

```bash
solve https://github.com/owner/repo/issues/123 --auto-merge --auto-fix-ci-cd
```

Эти параметры также работают в Telegram `/solve` и `hive`. Опция выключена по умолчанию; без `--auto-merge` проверка аргументов отклоняет её.

После подтверждения слияния GitHub solver проверяет фактическую целевую ветку pull request. Он получает последний запуск каждого активного workflow для ветки и запуски на текущем коммите ветки, включая публикацию по тегу. Ошибки, отмена, тайм-аут и неизвестный результат workflow считаются ошибками. Выполняющиеся workflow и отсутствующие запуски остаются в ожидании.

Намерение публикации определяется по активным workflow, манифестам пакетов и указанным локальным скриптам. Скрипты читаются, но не выполняются. Требуется подтверждение каждого обнаруженного результата:

| Результат      | Необходимое подтверждение                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GitHub release | Опубликован после слияния, коммит тега содержит слитое изменение; черновики не учитываются.                                  |
| npm            | Публичный npm registry содержит текущую версию из манифеста и время публикации после слияния. Приватные пакеты исключаются.  |
| PyPI           | Для текущей статической версии project/Poetry после слияния загружен дистрибутив.                                            |
| crates.io      | Текущая статическая версия crate опубликована после слияния. Исключаются crates с `publish = false` или `publish = []`.      |
| GitHub Pages   | Успешное развёртывание окружения `github-pages` либо сборка Pages из ветки после слияния, коммит которой содержит изменение. |

После исходного слияния могут появиться коммиты обновления версии. Проверка читает метаданные пакетов из текущего коммита целевой ветки и проверяет Git ancestry коммитов release и deployment. После каждого исправления она получает коммит слияния pull request этого исправления; продвижение ветки ботом публикации само по себе не подтверждает слияние исправления. Старый release или версия в registry не могут подтвердить новое слияние.

Успешный CI без release или deployment также считается ошибкой. Пропущенного шага публикации недостаточно. Если registry, динамическую версию или конфигурацию публикации нельзя проверить, solver сообщает об отсутствующем подтверждении. Прямая проверка registry поддерживает публичные npm, PyPI и crates.io. Распознанным публикациям NuGet, Maven/Gradle, RubyGems, Dart и Composer нужна дополнительная поддержка проверки; она также необходима для приватных registry и внешних reusable workflow. Неполная опись файлов и недоступные файлы остаются ошибками.

Монитор даёт одну минуту после слияния на появление отложенных workflow, ждёт CI до часа и даёт пять минут после завершения workflow на появление результатов публикации. `--verbose` выводит диагностику опроса и подтверждений.

При неудачной проверке solver создаёт Bug issue по существующему шаблону `/fix --ci-cd`, включая целевой коммит, ошибки workflow и отсутствующие результаты. Он решает issue с `--development-log --deep-analysis --auto-merge`, сохраняя параметры worker, например `--tool`, `--model` и `--think`. Каждое исправление использует новый checkout и сеанс инструмента в исходной целевой ветке. Родительский процесс снова проверяет CI/CD после исправления; дочерние solver не запускают вложенную цепочку исправлений.

Исправления расходуют общий бюджет родительского solve `--auto-restart-max-iterations` (по умолчанию 5). Значение `0` разрешает неограниченную цепочку. Исчерпание бюджета, ошибка дочернего процесса, неизменившаяся целевая ветка или прерывание приводят к ошибке команды; созданные issue/PR остаются доступны для проверки.

Справочники GitHub API: [releases](https://docs.github.com/en/rest/releases/releases), [статусы deployment](https://docs.github.com/en/rest/deployments/statuses), [сборки Pages](https://docs.github.com/en/rest/pages/pages) и [сравнение коммитов](https://docs.github.com/en/rest/commits/commits#compare-two-commits).
